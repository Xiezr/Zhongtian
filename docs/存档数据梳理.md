# 存档数据梳理 · 与新代码框架的核对

> 2026-11-23 · 依据老板「梳理存档数据，确认按新代码框架实现」
> 核对对象：`js/state.js`（存档）、`js/fog.js`（探明度）、`js/sphere.js`（球系）、`js/state.js` 的迁移链

---

## 一、机制（一句话）

**整份 `GAME.state` 序列化，只剔派生数据；版本不符直接作废，不存在"半迁移"状态。**

| 项 | 事实 |
|---|---|
| 存储键 | `sanguo_save_v3`（主档）+ `_s1/_s2/_s3`（手动槽）+ 独立的 `META_KEY`（轻量索引） |
| 版本 | `SAVE_VERSION = 3`；`st.version !== 3` → `clearSave()` 并返回 null |
| 序列化唯一出口 | `GAME.savePayload()`（导出/槽位复用同一份，不许各写一份） |
| 实测体积 | 新局 **6 KB**（上限 5 MB，余量充足） |

### 被剔除的派生数据（不入档，读档时重建）

| 字段 | 体积 | 为什么剔 |
|---|---|---|
| `map.grid` | 9 MB（25 万格） | 曾撑爆 5MB 配额导致存档静默失败；地形由 `map.seed` 重建 |
| `map.cities` | 54 KB（174 城） | 守军从不被修改（纯派生）；且读档用旧副本会让改数值对老档不生效 |
| `_sub153LL` | 1.5 MB | 格网迁移的经纬缓存，迁移完成后再无人读 |
| 日志 | 按 `LOG_KEEP` 截断 | 只留最近 N 条 |

## 三、与新代码框架的核对

| 检查项 | 结论 | 证据 |
|---|---|---|
| 星球框架（v91.25 起） | ✅ 在档 | `mapPlanetId`、`planets[]`、`activePlanet` 三者齐备 |
| 探明度（v92 打包） | ✅ 在档 | `fog = {v:2, sig, n, data:'base64'}`，`n` 与当前格网一致 |
| 地形 | ✅ 不入档 | `map.grid` 被 replacer 剔除；读档由 `map.seed` 重建 |
| 前传（v157.85 下线） | ✅ **零残留** | 全档无 `prologue` 键；源码里只剩墓碑注释 |
| 痕迹（v157.98 下线） | ✅ **零残留** | 全档无 `trace` / `traceChance` |
| 球系格网迁移 | ✅ 幂等 | `_sub153` 标记保留、`_sub153LL` 缓存剔除 |
| 玩家位置（v157.96） | ✅ 自动入档 | `_standCi` 属于 state；传送后重启仍在（本轮新增字段，无需改存档结构） |
| 老档 | ✅ 直接作废 | `v2` 实测被清除，不会半迁移 |

**结论：存档结构不需要为新框架改任何东西** —— 它是"整份 state + 剔派生"，
新字段天然入档、下线系统天然出档。真正要防的是**派生数据回潮**和**旧键残留**，这两条已固化成断言。

## 四、发现的两处（都不影响运行）

1. **`createdAt` 只写不读**（`state.js:732`）。建档时写入，全项目无读取方。
   保留为存档元信息（10 字节），**不建议现在删** —— 删了没有收益，反而少一个"这档什么时候建的"。
2. **`cities` 占存档一半**（2.9 KB / 6 KB）。当前规模无风险；
   若将来城市数大幅增长，它是第一个需要拆分的对象。
