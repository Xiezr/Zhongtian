## 二、地图上的"我在这"

前传是君主一个人在大地图上走，但屏幕上**没有任何标记指向自己**——
视野区域的中心就是自己，可玩家不知道中心在哪。

先核对了索引：`_tileCells = SP.cells`（map3d.js:252/278），
所以 `mark[ci]` 与消费端 `_tileCells[ci]` 是**同一套索引**（之前担心是两套）。

加了两样：

| 元素 | 做法 |
|---|---|
| 脚下这一格 | 平涂亮金 `[255,216,92]`，`cellKind='lord'` |
| 头顶标签 | `floatName(dir, '▲ 你', '#ffe28a')` |

标记写在 `fogHides` 过滤**之后** —— 脚下必然已探明，放后面省得被雾判掉。

> ⚠️ 踩了一次：`floatName` 内部用 `grp`/`lp`（`var` 声明，会提升但值为 undefined），
> 第一版在 `var grp = new THREE.Group()` 之前就调用它 → 必然崩。移到定义之后才对。

## 三、点名斗将

### 内核是现成的，缺的是入口

`battle.duelPlay` 早就有：4 招相克（突刺→蓄力→佯攻→格挡→突刺）、5 合先到 3 分、
对手倾向由四维推（武力→突刺 / 统率→格挡 / 谋略→佯攻）。

前传补的是：**谁能斗、怎么逐合出招、输了怎样**。

### 规则

| 项 | 设定 |
|---|---|
| 入口 | HUD 的「⚔ 点名斗将」，**这格有动作时**才出现（纯荒地没人应战） |
| 每格次数 | **只叫一次阵**（`prologue.dueled`）—— 不设这条就是刷经验捷径 |
| 对手 | 该格守将；等级超过「君主等级 × 1.5 + 10」则换成本档的"游荡者" |
| 成本 | 2 精力（叫阵），输了再 −25 体力 −15 精力 |
| 胜 | 经验 = 对手等级 × 25 + 1 件辐能核心，**并且这格头目服了** |
| 平 | 经验 = 等级 × 15 |
| 负 | 经验 = 等级 × 8（打输也学到东西） |

### 最重要的设计点：赢了有什么用

清剿一次给 **4,000+ 经验**，斗将只有几百 —— **单看经验没人会斗将**。
所以它的价值放在别处：

> **斗将胜 → 这格的头目服了 → 之后 3 次战斗类动作难度 −40%**

接的是现成的 `def.power` 临时缩放（`P.act` 本来就在用它做前传倍率）。
只对 `fight / trial / scene` 生效 —— 采集/静修没有对手，不该跟着变便宜。
用完递减，3 次归零。

这才让斗将有了位置：**打不过的时候，先把头目挑下来。**

### 实跑撞出的两个真 bug

#### ① 比分当场倒退（"每合换人"）

```
第1合 我出 guard → 1:0
第2合 我出 guard → 1:0
第3合 我出 feint → 0:1      ← 比分从 1:0 变成 0:1
```

根因：`duelStep` 每合用**累积出招**重算前 N 合（这样才不必自己写第二套判定），
而对手出招的种子是 `'duelm|' + defGen.id + '|' + round + '|' + seed`。
`duelFoe` 每调一次 `makeGeneral` 就拿到一个**新的自增 id** ——
于是"重算前 N 合"时其实换了一个对手，招式序列全变。

修：把对手 id 钉成 `duelfoe_<ci>`。

#### ② 我写的风险提示是错的

第一版写的是「Lv1 对 Lv100 —— 这一战是送」。
核对内核后才发现：**`duelPlay` 的胜负只看招式相克，等级与四维完全不参与**。
它们唯一的作用是决定"对手爱出哪一招"的**权重**。

所以真正决定成败的是「他的倾向读不读得出来」：

- 四维偏科的对手 → 权重集中在某一招 → **看得出来** → 猜对就能赢
- balance 型守将（90/90/90）→ 三项权重几乎相等 → **读不出来** → 只能赌

面板改成只说这件事：

```
对手 Lv12　统90 勇90 智90 政90
看他架势：四平八稳 —— 读不出偏哪一手，只能临场赌
⚠ 这人没有明显路数，五合里全是猜
```

（可读性判据：最强项 / 次强项 ≥ 1.15）

### 验证

用**预演穷举**找必胜序列（4^5 = 1024 种），再按序列真点：

```
bestSeq  = [guard, stab, guard, charge, feint]   bestScore = 3
duel     = 斗将胜 3:0 —— 这片的头目服了 · 经验 +300
subdued  = 3   （头目服了，3 次优惠）
subduedAfter = 0  （做了 4 次战斗动作后归零 → 递减在工作）
```

**诚实标注**：`power × 0.6` 我做了什么验证 ——
只验证了 `subdued` 的**递减链路**（3 → 0），**没有做成功率分布验证**。
代码接线是明确的（`P.act` 里 `* (_subdued ? 0.6 : 1)`），
但"难度真的降了 40%"这件事，最好用 20 局对照成功率来证，这轮时间不够。

### 防复发（两条断言）

| 断言 | 判据 |
|---|---|
| `§326⑩` | 同一格两次取 `duelFoe` 必须是同一个 id 与等级（防"每合换人"） |
| `§326⑪` | 同 seed + 同出招序列 → 同比分（斗将可复算的前提） |

## 五、这轮的教训

1. **"形状检查拒绝合法状态"是最阴的一类 bug** —— 它不报错、不崩，
   只是让存档静默失效。玩家看到的是"进度没了"，日志里什么都没有。
   放宽判据时必须同时写**反向断言**（§326⑨），否则就是拿防线换方便。
2. **改别人的内核之前先读它** —— 我按"等级决定强弱"的常识写了风险提示，
   而 `duelPlay` 根本不用等级。差一步就把一个错误提示交出去了。
3. **"重算式状态"要求所有输入都确定** —— 累积出招重算是省事的好办法，
   但对手的 id、种子、四维任何一个不确定，结果就会漂。
4. **我自己的验证也可能只验了一半** —— `power ×0.6` 只验了递减、没验效果，
   这条写在报告里，不装作验过了。
