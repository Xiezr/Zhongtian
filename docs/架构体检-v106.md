## 二、决定：不重构，上棘轮

### 为什么不做

- state 249 个出口、被 46 个模块依赖、18 组循环。拆它等于重做状态层加载顺序，
  而全项目 **4049 条 smoke + 1101 条 e2e** 都是以现在的顺序为前提写的。
  收益是"文件变好看"，成本是"可能半年不稳"。不划算。
- ui.js 1.25MB 确实大，但它 44 个面板的渲染逻辑一旦迁走就要重排 e2e 的选择器假设。
  注册表（v100）已经把"新模块"的入口统一了 —— **新债不欠**，老债不强还。

### 做什么

1. **修 bug**：`prologue.js` 写 `GAME.staMaxOf`（不存在），因为判空所以**静默失效**，
   前传的体力永不恢复。改 `GAME.staMax`。
2. **立层规矩**：三层 = 三包；core 引用 war/ui **一律判空**（只加载 core 的探针会静默跳过）。
3. **上棘轮**：`arch-baseline.json`（63 对）+ `selfcheck` 第 8 项。
   新增跨层依赖当场红，主动还债后 `--write` 压低基线，**基线只降不升**。

### 棘轮自证（门禁必须能红，否则等于没有）

往 `prologue.js` 注入一行 `GAME.ui.nopeProbe`：

```
❌ 跨层引用比基线多了 1 处：
   core>ui prologue>ui 0 → 2
expect-fail-exit=1
```

撤销后回到 `✅ 63 对跨层引用，无新增`。

## 三、留给以后的三件事（按收益排序）

1. **domain → main 的 208 处**：业务层调动作函数。正确做法是把这 106 个 `GAME.doXxx`
   按域搬进各自模块（建造类进 domain、界面类留 main）。**一次搬一个域，搬完跑全量。**
   这是唯一能真正降低 core→ui 的改动，也是风险最高的，需要专门一轮。
2. **state 的生产结算段**（`cityProdPerSec` / tick 主循环）单独抽成 `js/prod.js`。
   它是最热的一段代码，也是我这两轮反复加闸门的地方 —— 抽出来加闸门更安全。
3. **data.js 按域拆**（世界 / 物品 / 战斗 / 界面文案）。纯数据，风险低，收益也低，
   等 2 做完再看。

## 五、v113 修正：量具错了，真实跨层是 **28 对**，不是 63 对

`--check` 的棘轮要求"基线只降不升"，但**基线本身算错了**：

`GAME.state` 是 state.js 里的核心对象，而 main.js 在**删档**时写了一次
`GAME.state = null`。我的归属逻辑是"任一文件赋过值就算它定义"，
于是 `GAME.state` 被算成"main 定义的槽"——
`domain → main` 于是虚报 **208 处**，其中 **204 处其实是 `GAME.state`**。

修正：归属只取**按 ORDER 最先定义它的那个模块**（= 加载顺序里的主定义）。

| 指标 | 修正前 | 修正后 |
|---|---|---|
| 跨层模块对 | 63 对 | **28 对** |
| core → ui | 58 处 | **19 处** |
| domain → main | **208 次** | 4 次 |

**这意味着「domain → main 208 处」这条债根本不存在。** 我在 v106 把它列为
"收益最高、风险最高的第一件事"——那是错的，基于一个坏掉的量具。

教训：**先证明量具是对的，再用它做决定。** 门禁能撒的谎不止"假绿"，
还有"假红"（把一个不存在的问题报成头号债务）。

## 六、prod.js 抽取：本轮**不做**（决定 + 理由）

原计划第 8 项：把 `state.js` 的生产结算段抽成 `prod.js`。理由曾经是
"它最热、也是反复加闸门的地方"。现在不做的原因：

1. **它和 20 多个模块的月度结算是同一个 tick 循环里的**。抽出去要改
   `GAME.reg.tickAll()` 的调用顺序，而"顺序"正是这个项目最脆的东西
   （104 个模块的求值顺序、注册表 order、tick 的先后，任何一处挪动都会改世界）。
2. **它对性能敏感**。100 城压测的 `tickOnce < 6ms` 是既有断言，
   搬家会先让这个数变难看，再慢慢修——属于"为了好看先制造一个性能问题"。
3. **明天要复核**。不该在复核前夜留一个"引擎核心正在搬"的中间态。

真要做的正确姿势（留给下一次）：
先给 `cityProdPerSec` 加**每秒调用次数**的计量（现在没有），
拿到真实热路径数据，再决定搬哪一段——而不是凭"感觉它很热"。
