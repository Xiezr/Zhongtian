# v89.119 交付说明 · 反击记录配对（「反击和对方出手记录在同一行」）

> 老板原话（逐字）：
> 「反击应该在敌方出手后，而不是己方移动后直接反击，回合记录稍微调整。我方移动，出手，对方反击（如有）；
> 对方移动，出手，我方相应反击（如有）。反击和对方出手记录在同一行」
>
> 门禁：**audit 0/0/0/0/0 · smoke 2800/0 · e2e 1061/0**（`python .workbuddy/tools/git/gate.py --full` 退出码 0）
> 实机：2 张图 + 像素体检全过（`.workbuddy/tools/asset/check_v89119_shots.js`）

---

## 1. 病根（一句话）

**反击事件被归到「反击者自己的行」里、且行内排在它自己出手之前** ——
读起来像"我方（先）反击、（后）出手"，而**引发这次反击的那次敌方出手根本不在同一行**。

### 1.1 取证（`probe_v89119_counter.js`，场景3 第 4 回合）

改前（同一份事件流的两行）：

```
·[我] 长枪兵　反击 → 轻骑兵 歼 585 · → 轻骑兵 歼 585 · 反击 → 刀盾兵 歼 140
```

- 「反击 → 轻骑兵」是**回应轻骑打它**的；「→ 轻骑兵」才是它自己出手；
  「反击 → 刀盾兵」又是**回应刀盾打它**的 —— 三次动作挤在一行，因果全乱。
- 老板看到的：「**反击**」出现在行首（移动/出手之前）、且像"打了两遍同一个目标"。

### 1.2 引擎侧的真实时序（没病，病在记录）

引擎事件流本来就是对的：

```
[move] def 轻骑兵 step=394
[attack] def 轻骑兵 → 长枪兵 歼 466      ← 轻骑出手
[attack] atk 长枪兵 → 轻骑兵 歼 784      ← 长枪出手
[counter] def 轻骑兵 → 长枪兵 歼 374     ← 轻骑**挨打后**反击（紧跟那次出手）
```

**唯一出口的配对规则**：`counter.targetId === 某次 attack 的 id`，且阵营相反（键带阵营前缀，`a|id` / `d|id`）。

## 2. 改法

| | 改前 | 改后 |
|---|---|---|
| 反击的归属 | 归到**反击者自己的行**（自成一行/一截） | 并入**引发它的那次出手**（同一行、紧跟其后） |
| 行内顺序 | 反击排在该单位「出手」之前（`moves.concat(acts)` 的偶发顺序） | 移动 → 出手 → （对方反击） |
| 文案 | `反击 → 目标 歼 N`（谁反击谁要读者推） | `（对方X反击 歼 N）` —— 用老板原词「对方」 |
| 战报纪要 | 反击独立成段（`；X(敌) 反击 Y 杀伤 N`） | 并入出手段：`… → Y 杀伤 N（对方X反击 杀伤 M）` |
| 回放帧 | 反击独立成段 | 并入出手段（同口径） |
| 落点 | 三处各写一份 | 三处同一配对规则（见 §3） |

**目标形态**（老板给的句式，逐字落地）：

```
[我] 长枪兵　进 309 · → 长枪兵 歼 60（对方长枪兵反击 歼 35）      ← 我方移动、出手、对方反击
[敌] 长枪兵　→ 长枪兵 歼 35（对方长枪兵反击 歼 54）              ← 对方移动、出手、我方相应反击
```

---

## 3. 三处落点（同一配对规则）

| # | 文件/函数 | 用途 | 说明 |
|---|---|---|---|
| ① | `js/tactic.js` · `finish()` 的回合纪要 | 战报正文「第 N 回合：…」 | 反击并入出手段，多个反击用「，」并列 |
| ② | `js/ui.js` · `ui.btRoundLines` | 实时战斗界面下部分回合记录 | 反击**不再自建行**；行 = 行动者（移动·出手·对方反击） |
| ③ | `js/battle.js` · `replayFramesOf` 的 `evLine` | 战报回放帧摘要 | 同口径（`（对方X反击 杀 N）`） |

* 配对键 = **对面阵营 + 出手者 id**（`a|id` / `d|id`）—— **同名兵种互射不串台**（弓手 vs 弓手的实测见 §4.3）。
* **兜底**：找不到宿主的孤立 counter（异常数据）→ 独立成格/成段，**不静默丢事件**（有断言钉死）。
* 沙盘的**逐帧动画**（`ui.sdLine`）与实时战斗的**逐条闪烁字幕**（`ui.btEvent`）保持原样 ——
  它们是"与动画同步的逐条流"，不是回合记录；本轮的「同一行」指回合记录三处。

## 5. 顺带修掉的两个既有问题（实机抓出）

### 5.1 「把函数当布尔传」的**恒真断言**（6 处）

`smoke-test.js` 的 `check(name, cond, extra)` 里 `if (cond)` **不调用函数** ——
把 `function () { return X; }` 当第二参传进去 → 函数对象恒 truthy → **断言恒过**。

- 本轮在 **§98（v89.118 遗留）2 处** + **§100（本轮）4 处**抓到，全部改成 IIFE / 求值。
  §98 那两条改成真判据后**仍然通过**（逻辑本身是对的，只是判据形式恒真）——
  但"是否真的在起作用"从今天起才被真正验证。
- **制度性防护**：`audit.js` 新增**第 ⑦ 节「恒真断言」**——扫描 `check(` 的第二参，
  `function` 开头且**不是立即调用**（无 `}()`）即报；`--strict` 下计入退出码。
  审计器做了**自检实验**：临时造一条坏 check → 报警 1 处 → 还原 → 0 处（md5 一致）。

### 5.2 战报正文页溢出（既有载荷问题，本轮一并修）

- 实机量测（1000 高视口 / 13 回合 / 7 兵种真实载荷）：`.inner-panel` 内容 1059px vs 可见 840px → **溢出 219px**。
- 逐段定位：简报 **251** · 回合纪要 235 + 分页 44 · 兵种损耗表 169 · 回放小节 120 …
- 三刀收紧：
  1. **去重**（`ui.stripBodyDup`）：简报里的「【兵种损耗】…」文本段与下方结构化表（`rp-tbl`）是同一份信息
     重复两遍 → **渲染时剥文本版**（`report.body` 本体不动，列表摘要/旧档照旧）；
  2. 回合纪要分页 **5 → 3 行/页**；
  3. 该页专属加高 **modal-tall**（`min(920px, calc(100vh - 40px))`）—— **不动 xxl 本体（1200×850 冻结点）**。
  顺带清掉 `index.html` 里 **两处一字不差的 `.modal-xxl` 重复定义**（后者空转）。
- 结果：**溢出 0**（h=920）。

## 7. 诚实缺口

1. **沙盘逐帧动画**（`ui.sdLine`）里反击仍是独立一帧 —— 它与动画时间轴同步（帧到才播），
   合并会改变闪烁时机。本轮的"同一行"按**回合记录**口径落（行/纪要/回放帧三处）。
2. **旧档战报**（已存盘的 `report.body`）里的回合纪要是**当时写死的文本** —— 重看旧战报时仍是旧格式
   （战报正文不回算，这是既有设计）。新打的战报一律新格式。
3. **回放帧**（`replayFramesOf.evLine`）有"每回合最多 3 段"与 56 字截断 —— 配对后段数变少、
   信息更紧凑，但极端长帧仍可能被截断（既有行为，未改）。
4. **战报正文页 modal-tall 在 ≤820 高视口**下会被 `calc(100vh - 40px)` 压回 ——
   该页在小屏仍可能溢出（项目一直桌面横屏口径，窄屏专项见遗留 #9）。
5. `ui.stripBodyDup` 的判界规则是"下一个以【开头的段" —— 若**未来** battle.js 在损耗段中间插入
   不以【开头的**新段**，会被误并进损耗段一并剥掉。已在函数注释里写明规则；
   加段时要么用【开头，要么调整该函数（有断言覆盖三种常见形态）。
6. 恒真断言扫描只覆盖 `check(` 的**第二参**（标准调用形态）；若有人写成
   `check(name, (cond), extra)` 之外的变体（如先赋变量再传函数），扫描不到 —— 属"防呆"而非"防恶意"。
