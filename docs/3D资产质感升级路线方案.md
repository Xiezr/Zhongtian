# 3D 资产质感升级路线方案（废土残破城堡 + 花草树木 · 冲更高保真）

> 来源：2026-11-14 老板口头需求「能不能找到更漂亮的 3D 资产（花草树木、城堡建筑），或者把现在这些
> 做得真有 AAA 质感」。经 AskUserQuestion 确认三处分叉：
> **① 风格 = 废土残破城堡（藤蔓/苔藓/崩塌，融入《余烬纪元》废土世界观）；
> ② 质感档位 = 冲更高保真（需扩 gltf.js 解析器支持 roughness/AO/环境反射）；
> ③ 第一步 = 先出方案文档（暂不下载，方案过目后再动）。**

---

## 结论（先行）

1. **路线完全可行**：项目现有的 `gltf.js`（`js/bundle-war.js`）已支持「受光材质 + 法线贴图」，
   "表面有层次、有明暗"已具备；当前缺的只是**植被与城堡模型资源**本身（现 `assets/` 仅有
   actors 与 wonders，零植被/城堡）。
2. **"冲更高保真"需要一段解析器扩展**：现有解析器只吃 `baseColor + normalMap + 标量 metalness/roughness`，
   不吃 `roughnessMap/AO/envMap`。要 PBR 级质感，必须先补这层（见第五节），否则金属发黑、表面无微细节。
3. **资源全部可走 CC0**：花草树木首选 Quaternius Stylized Nature MegaKit，城堡模块化件首选
   3dassets.dev（均 CC0、GLB 内嵌贴图、米制 +Y-up，直接喂现有管线）。
4. **本方案是"先出文档"**：不含任何下载/接入动作；落地待老板过目后按第六节分步执行。

## 一、目标与风格定位

| 维度 | 决策 |
|---|---|
| 植被（花草树木） | 废土生态：枯荣混合的树、灌木、草丛、野花、苔岩——不追求"鲜绿花园"，而要"荒原里挣扎的生命" |
| 城堡建筑 | **废土残破城堡**：被自然吞没的古城——藤蔓攀墙、苔藓斑驳、局部崩塌、旗杆歪斜 |
| 融入方式 | 作为"奇幻/遗迹生态区"新 biome，与现有科幻奇观（戴森残片、母体舰等）并存，世界观自洽 |
| 质感目标 | 风格化 PBR（有 normal/rough/AO + 受光 + 轻量环境反射），非照片级扫描 |

---

## 二、质感档位决策：冲更高保真 → 解析器扩展是前置

当前 `gltf.js`（`js/bundle-war.js:169-266`）材质能力：

| 能力 | 现状 |
|---|---|
| `baseColorTexture` → `map` | ✅ 支持 |
| `normalTexture` → `normalMap` | ✅ 支持（v91.38 起） |
| `metallicFactor` / `roughnessFactor` | ⚠️ 仅**标量**；metalness 被夹到 ≤0.25（无 env 时防发黑） |
| `metallicRoughnessTexture`（ORM） | ❌ 未接 → roughness/AO 变化丢失 |
| `emissiveTexture` | ❌ 现用 `emissive = baseColor` 近似（v91.38 妥协） |
| 环境反射 / IBL | ❌ 无 → 这是"质感"天花板的最大约束 |

**结论**：不扩解析器，"更高保真"无从谈起。第五节给出最小扩展集。

## 四、接入架构

| 层 | 方案 |
|---|---|
| 目录 | `assets/nature/{trees,plants,rocks,grass}`、`assets/structures/{castle_modular,castle_hero}` |
| 加载 | 复用 `GTF.parse` + `GTF.bakeGeometry` + `GTF.buildMaterial`（扩后自动吃 PBR） |
| 散点 | 地形按 biome 随机散布，复用 `map3d.pickGroundPoint` 取样；种子固定保证可复现 |
| 批量 | 草/灌丛用 `InstancedMesh`（需新增 scatter 工具，当前解析器返回单 Geometry）；英雄树/城堡件用普通 Mesh 分组 |
| 废土化 | 对"干净"城堡模型做"自然吞噬"：叠加 Quaternius 花草包里的藤蔓/苔藓贴片；崩塌用模型破损版或旋转/下沉随机化；统一降饱和调色 |
| 优化 | 接入前用 `gltf-transform` 跑一遍：quantize + 贴图 resize 到 webp + 去冗余，控体积（参考 wonders 既有的"单 mesh + 少量 webp"规整结构） |

## 五、解析器扩展方案（最小集，先落地再扩）

**Phase 0 解析器（落地前置）**—— 改 `js/bundle-war.js`：

1. **ORM 贴图**：解析 `pbr.metallicRoughness.metallicRoughnessTexture`，按 glTF 标准分包
   R=metal / G=rough / B=AO → 设 `metalnessMap` + `roughnessMap` + `aoMap`。
   ⚠️ `aoMap` 需要第二套 UV（`uv1`）；若模型仅 `TEXCOORD_0`，复制一份或降级忽略 AO（不阻断）。
2. **真·自发光**：解析 `pbr.emissiveTexture` + `emissiveFactor` → `emissiveMap`，替换当前
   `emissive = baseColor` 近似（背光面不再死黑、且不再污染非自发光面）。
3. **轻量 IBL（质感关键）**：用 `THREE.PMREMGenerator` 从**程序化天空/现有场景**生成 `envMap`
   挂到 `scene.environment`——项目零外链，用程序化渐变或内置简易 env（不引 HDRI 外链）。
   这是让 metalness/roughness 真正"有东西可反射"的前提；否则仍会被夹到 ≤0.25。
4. **暂不入**：`KHR_materials_clearcoat / transmission` 等扩展超出范围。

**性能**：植被/草场必须 `InstancedMesh`；`buildMaterial` 接受共享材质（同套贴图的树只建一次材质）。

## 六、分步落地（方案过目后执行）

| 阶段 | 动作 | 出口判据 |
|---|---|---|
| **Phase 0** | 扩 `gltf.js`（ORM + emissiveMap + 程序化 env）；拿一个现有 wonder GLB 验证"更质感" | 解析器单测：贴图通道全部命中、env 反射可见、零回归（smoke/e2e 不红） |
| **Phase 1 · pilot** | 下 **1** 个植被样本（Quaternius 一棵树）+ **1** 个城堡模块（3dassets.dev 城门）→ 解析 + 放进测试场景 + 截图 | 管线能吃这种 GLB；废土化（藤蔓/苔藓/崩塌）观感达标 |
| **Phase 2 · 小批量** | 下 Quaternius 自然包子集 + 3dassets.dev 城堡件子集 → 接入散点/模块化拼接 | 生态区可辨识；帧率达标（InstancedMesh 生效） |
| **Phase 3 · 全量 + 风格统一** | 全包接入 + 藤蔓/苔藓叠加 + 统一降饱和调色 + `gltf-transform` 压缩 | 全 biome 可用；体积/性能达标；CC0 合规 |

## 七、风险与回退

| 风险 | 缓解 |
|---|---|
| 许可踩雷 | 只用 CC0；非 CC0 单列 CREDITS 并报批 |
| 体积膨胀 | gltf-transform 压缩 + webp；hero 件才高精度，草用低面数 |

| 解析器扩展引入回归 | Phase 0 先单测 + 全量 gate；回退点 `.workbuddy/backup/` 整文件覆盖 |

## 八、已拍板（2026-11-15 老板过目方案后定）

> 本文件为纯方案，未做任何下载/写入 `assets/`。落地指令自 2026-11-15 起按本节下发。

| # | 决策点 | 老板拍板 | 参谋长备注 |
|---|---|---|---|
| 1 | 城堡形态 | **单体地标（AutoSprite，快但不可拆）** | 取舍已明确：放弃模块化拼装的灵活度，换"快上、零拼装风险"。废土化靠材质/贴片叠加，不靠拆件重组 |
| 2 | 废土残破程度 | **轻做旧（干净 + 苔藓）** | 不进重崩塌/藤蔓封门；苔藓=贴片/着色叠加，统一降饱和即可，观感最稳 |
| 3 | env 反射 | **接受程序化 env（无 HDRI 外链、零依赖）** | 用 `THREE.PMREMGenerator` 从程序化天空/现有场景生成 `envMap` 挂 `scene.environment`，不破零外链铁律 |
| 4 | 第一步 | **先动 Phase 0 解析器**（参谋长拍板，理由如下） | 解析器是硬前置：先下 pilot 样本时管线还吃不了 roughnessMap/AO/emissiveMap 更无 env，样本放进去也达不到"更高保真"；Phase 0 用现有 wonder GLB 即可验证"更质感"（零新资源风险），再让 pilot 在已具备 PBR 能力的管线上验证资产接入 |

**第 4 项参谋长拍板理由（补录）**：
- 解析器是硬依赖。若先 pilot，管线此刻仍缺 `roughnessMap`/`aoMap`/`emissiveMap` 且**无 env 反射**——样本进去只是"干净原模"，根本达不到目标，等于验证了半套不能用的管线。
- Phase 0 用**已有 wonder GLB** 就能验证"更质感"（零新资源风险），先跑通 ORM/自发光/程序化 env 且门禁不红，再让 pilot 样本在"已具备 PBR 能力"的管线上验证资产接入——正是第六节 Phase 0 出口判据的设计意图。
- 反方（先 pilot）唯一好处是早看真实废土化观感，但废土化是 Phase 2-3 的事，Phase 1 只验证"能吃这种 GLB"，不必抢跑。

**落地约束（重要，v157.56 教训）**：`js/bundle-war.js` 是 `build_bundle.py` 按 `js/modules.json` `layout.war` 拼接的**构建产物**，真正源码是 **`js/gltf.js`**。所有解析器改动必须落 `js/gltf.js` 后重建，绝不可手改 `bundle-war.js`。
