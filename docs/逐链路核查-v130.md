## 二、P0-1：前传 HUD 压住所有弹窗（v128 引入的回归）

### 现象

出征面板打开后，「🚩 占领 / 🔥 掠夺」按钮**可见、未禁用，但点不动**：

```
page.click('#modal-root [data-action="exp-confirm"]')
→ Timeout 5000ms exceeded（元素存在、可见、未被禁用）
```

`elementFromPoint` 命中的不是按钮，而是前传层的一个空白 `DIV`。

### 根因（层叠上下文，不是 z-index 数值不够）

| 节点 | position | z-index | transform | 所在栈 |
|---|---|---|---|---|
| `#app-scale` | relative | auto | **`matrix(1.0556,…)`** | 根栈，**自成层叠上下文** |
| `#modal-root .modal-mask` | absolute | 1000 | none | **在 `#app-scale` 内部** |
| `#prologue-screen`（v128） | **fixed** | 70 | translateX(-50%) | **挂在 `body` 上 = 根栈** |

`#app-scale` 带 `transform: scale()`，因此它是一个**独立的层叠上下文** ——
内部 `.modal-mask` 的 `z-index:1000` 只在它自己那一层里有效，**对外等于 `auto`**。
而前传层挂在 `body`、`z-index:70`，直接和 `#app-scale` 这一整块比大小 → **70 > auto，前传层赢**。

v128 把前传从"全屏黑底"改成"底部 HUD"时，保留了 `position:fixed` 与挂 `body` 的旧写法，
于是 HUD 从"盖住地图"变成"盖住地图 + 盖住所有弹窗"。

### 影响面

前传持续到君主 Lv20（约 9 场），也就是说**每一个新玩家的第一小时**里，
任何从底部弹出确认键的面板（出征、建造、升级、装备）都可能点不动。

### 修法

把前传层挂进 `#app-scale`、定位改 `absolute` ——
与 `.modal-mask` 当年 `fixed → absolute` 是同一个理由（整幅画面统一缩放，画布是唯一坐标系）。

### 验证

```
④ 前传 HUD 必须挂在 #app-scale 内   → 父节点=app-scale   ✅
⑤ 按钮位置在最上层                  → 该点最上层=BUTTON   ✅
```

修后全链路实跑：出征 20000 兵 → 3500 兵（扣 16500），队列 1 支，
补算后自动打完一仗、战报 1 条、损失与战利品入账。

## 三、P0-2：迷雾衰减节流从未生效（单字符 bug，且断言与代码犯同一个错）

### 现象

一次 `simulateSeconds(3600)`（1 小时游戏时间）产生 **131 条公文**，其中：

```
56 × 🌫 远方的记忆淡了：N 格转为半明（城与前哨周围不受影响）
 7 × 天时：晴 / 雨 / 雪 / 大风
 7 × 🚶 门外那批流民等不到答复，走了
12 × 🏺 科技升至 LvN
```

**43% 是同一句话**。真正的战报只有 1 条，被挤到看不见。

### 根因

```js
// js/fog.js（修前）
var last = st.fogDecay | 0;        // ← 32 位整数截断
if (!force && now - last < hours * 3600000) return 0;
```

`st.fogDecay` 存的是**毫秒墙钟** `Date.now()`（约 `1.79e12`，41 位）。
`| 0` 会把它截成低 32 位：

```
1792779649426 | 0  ===  1778286994      // 等价于 1970 年附近
now - last         ===  1792777872433ms ≈ 20.7 天
20.7 天  >>  12 小时   →  节流永远通过
```

实测钩子（600 次调用）：

| | 修前 | 修后 |
|---|---|---|
| `F.decay` 被调用 | 600 次 | 600 次 |
| 真的执行衰减 | **56 次** | **0 次** |
| 公文增量（10 分钟游戏时间） | 27 条 | **15 条** |
| 1 小时总量 | 131 条 | **84 条** |

所以 `decayHours = 12` 这个设定**从上线起一次都没生效过**。
实际行为是"玩家每点亮一格视野，下一个 tick 就被抹掉并写一条日志"。

### 更值得记的一点：断言和被测代码犯了同一个错

```js
// smoke-test.js §286⑮（修前）
return n === 0 && (G.state.fogDecay | 0) > 0 && ...
//                 ^^^^^^^^^^^^^^^^^^^^^ 同样的 32 位截断
```

截断后仍是正数 → 这条断言**永远通过**。
它不是"没覆盖到"，而是"用同一个错误去验证另一个错误"，所以绿灯亮得很安心。

### 修法与守卫

```js
var last = +st.fogDecay || 0;      // 一元 + 转数，毫秒时间戳不截断
```

新增两条：

- `§286⑮` 判据改为 **`G.state.fogDecay > 1e12`**（毫秒精度完整性）
- `§286⑮b` **"12 小时内第二次调用必须被拦住"** —— 这条在 bug 存在时必然拿到 `n > 0` 而失败

后一条是真正的守门人：它测的是**行为**，不是字段长相。

## 四、P1：前传的"立城"是假动作（数据与叙事的矛盾）

这是本轮唯一**没有动手**的一条，因为改它要动 `newGame` 的造城时序，
会牵动 324 处直接调 `newGame` 的测试基线 —— 不是能顺手吞下的改动。

### 实测取证

```
① 前传 HUD 说：「你们 200 个人，还没有城 —— 得找点能打的，先把人练出来。」
   实际 state：城 1 座 → ["新城市"] · 当前城=新城市

② 前传期间打开城市页（setView('city')）：
   → 成功，页面有 20 个「居所 1」+ 载具研究所 / 传送站 / 瞭望塔 / 战储仓

⑤ 点「立城（Lv20 已满）」：
   → P.build() 只调 P.end()，把前传标记关掉，**不建任何东西**
   → 立城前 cities=1，立城后 cities=1
```

### 为什么这是问题

前传唯一的戏剧目标就是"从没有城，到有城"。而现在：

- 城在 `newGame` 第 509 行就已建好（`id:'p1'`，名字取玩家输入的城名，默认为"新城市"）；
- 前传是在城**已经存在之后**才开始（`prologue.begin` 在造城之后调用）；
- "立城"按钮只是把 `prologue.on` 置 false。

所以前传期间玩家只要点一下底部的城市入口，就会看到一座有 20 栋建筑、有驻军、能出兵的城 ——
与"还没有城"直接冲突。v128 我把地图露出来之后，这个矛盾变得**一眼可见**（地图上就有一座城）。

### 三条可能的做法（需拍板）

| 方案 | 做法 | 代价 |
|---|---|---|
| A · 让叙事认账 | 前传文案改成"你们 200 个人，守着一座空城"，把目标从"立城"改成"把城撑起来" | 只改文案，不动结构。但前传的"从无到有"张力没了 |
| B · 让数据认账 | 前传期间不建城（造城推迟到 `P.build`），立城才真的落下第一座城 | 要动 `newGame` 时序，324 处测试基线要重跑；前传期间的地图/资源/采集都要能"无城运行" |
| C · 让界面认账 | 前传期间屏蔽城市入口与驻军操作 | 与 v128"让玩家看见世界"的方向相反 |

**我的判断**：B 才是根治，但它是独立一轮的活（需要"无城状态"这一整套支撑）；
A 是最小代价的止损。**这件事该由你定，我不擅自选。**
