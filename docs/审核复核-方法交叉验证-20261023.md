## 1. 路径一：用**项目作者自己写的工具**量同一件事

这些工具不是我写的，判据是作者自己定的（`fun-audit` 里甚至写死了"跨度 ≥8 点 = 是个有效决定"）。

### 1.1 `tools/balance-probe.js`（作者口径：战力/单位资源）

```
最高性价比：轨道炮车（229）· 最低：运输平台（14）→ 差 16.4 倍
  轨道炮车 229 · 重装机枪 181 · 步行机 168 · 迫击炮班 131 · 盾卫 124
  …泰坦机甲 35 · 无人轰炸机 28 · 东风快递 21 · 运输平台 14
```

我用的是**完全不同的方法**（等军资 1v1 对拼胜负，91 组），得到 **11 倍**落差。
两个数字（10.9 倍 / 11 倍）来自不同算法，却落在同一个量级——这类一致性比任何单一测量都可靠。

### 1.2 `tools/fun-audit.js`（作者口径：跨度 ≥8 点即"有效决定"）

它给出的结果是**反驳我的**：

```
② 动作：全体前进 74% / 全体驻守 100% / 全体后退 85%   → 跨度 26 点
③ 目标：死盯伏击车 74% / 死盯步行机 100% …            → 跨度 26 点
```

按作者判据，动作和选靶**都是有效决定**；而我上一份报告写的是"动作有 2 个严格劣、选靶 6/7 无差异"。这是直接冲突，必须查清。

## 2. 路径二：把"挑一个样本"换成"随机 200 个局面"

单点测量最大的问题不是算错，是**样本不代表分布**。于是我用作者自己的 harness（补满将领 + 半科技 + `withBoost`）
随机抽 200 个局面（Lv8~15、随机编成 4~16 万、随机守军构成），只问一件事：**换动作/换目标，战损差多少点？**

```
基准胜率 52%
              中位   p75   p90   最大   ≥10点的比例
动作（全驻守）   0     16    44    91      29%
选靶（兵种间）   0      0     5    70       7%
```

**这就是分歧的答案，两边都没说错：**

- 作者挑的那个 Lv12 样本，恰好落在"选靶跨度 26 点"的少数局面里 → 他量的是**条件结论**；
- 我挑的 Lv8 碾压局，恰好落在 93% 的多数局面里 → 我量的也是**条件结论**；
- 只有分布能同时容纳两者：**动作在 29% 的战斗里值得决策，选靶只在 7% 的战斗里有 ≥10 点影响（p75 = 0）。**

## 3. 我必须修正 / 撤回的两条

### 3.1 修正：P0-3「战术层是假深度」→「七成局面不需要战术，但不等于战术无效」

**我错在哪**（两个真错误，都出在探针初始化）：

| 错误 | 后果 |
|---|---|
| `makeGeneral(..., isStarter=false)` 且没调 `rankOf/guardFillOf` | 我的"玩家将领"属性没补满 → 多数战斗直接全灭 |
| 探针**完全没套** `battle.withBoost()`（半科技 + 0.12 加成） | 玩家侧赤手空拳，守军却有装备等效 |
| 第二次重跑时又把 `stances` 写成 `opts.plan` | 注入无效，200 个局面全部"跨度 0"——差点当成游戏结论 |

**修正后的表述**：
- 动作：**p90 = 44 点**、29% 的局面有 ≥10 点差 → 有决策价值，但七成局面无感；
- 选靶：**p75 = 0、93% 的局面差 <10 点** → 多数局面无感，少数局面（如 Lv13 的 30%→100%）能决定生死；
- 真正站得住的那句是：**"默认开智能战斗" + "多数战斗是碾压局" → 玩家实际感受到的决策空间接近零**，
  这是体验概率问题，不是"机制不存在"。

### 3.2 撤回：「Lv14 全灭、Lv15 反而能赢」的非单调曲线

那是我用"1.15× 战力"配平后测出来的，而配平用的 `power.armyOf` 又受残缺将领影响 → 曲线被扭曲。
用作者 harness（固定 7 万标准编成，逐级打上去）复测：

```
Lv 8 胜 0% · Lv 9 胜 16% · Lv10 胜 47% · Lv11 胜 60% · Lv12 胜 74% · Lv13~15 败 100%
```

**是一条单调恶化的曲线，在 Lv13 撞墙**——不是"Lv14 特殊、Lv15 翻盘"。原文那条撤回。

## 4. 路径三：黑盒复现性能（不信任我的任何内部测量）

我把整改前（`98db7ed`）的三个 bundle 从 git 取出来，单独起一个页面，
只用浏览器原生的 `PerformanceObserver('longtask')` 观察主线程——**不调用任何 `GAME.` 内部函数**，
人肉点一次「清剿」：

| | long task 数 | 总阻塞 | 最长单个 |
|---|---|---|---|
| 整改前 `98db7ed` | 5 | **14,991 ms** | **5,447 ms**（另有 2,407 / 2,390） |
| 整改后 `5d61feb` | 9 | **618 ms** | **79 ms** |

这条现在是整个报告里**最硬**的证据：它不依赖我对代码的理解，也不依赖我的计时器。

**顺便给自己打个折**：整改后最长 79ms **仍然超过 RAIL 的 50ms 建议值**（只是低于人可感知的 100ms）。
所以准确说法是"从 100 倍超标降到临界"，不是"完美"。

## 5. 哪些是外部标准，哪些是我的判断（这条最重要）

| 指标 | 有外部标准吗 | 来源 | 实测对照 |
|---|---|---|---|
| long task 阈值 50ms | ✅ 有 | Chrome / web.dev「RAIL 模型」：50ms 任务 + 50ms 渲染 = 100ms 响应预算 | 整改前 5,447ms = **109 倍** |
| TBT 桌面绿区 0–150ms、>350ms 红 | ✅ 有 | Lighthouse 官方阈值 | 整改前单次点击即 14,991ms |
| 响应时间 0.1s / 1s / 10s 三档 | ✅ 有 | Nielsen（1993），人机交互经典 | 7s 落在"注意力丢失"档 |
| 兵种性价比要"不倒退" | ❌ **没有行业标准** | — | 这是**设计常识**：投入更多应换来更多，不是更少 |
| 战斗"中位 9 回合偏短" | ❌ **没有标准** | 率土/三战 8 回合只是**对照案例**，不是标准 | 这条降级为"个人判断" |
| 综合 63.7/100、各维度权重 | ❌ **纯主观** | — | 删掉具体分数，只留"红/黄/绿"分级 |
| 可访问性（8 个 aria） | ✅ 有 | WCAG 2.2 / ARIA Authoring Practices | 属"未做"，但单机小众可降优先级 |

> **一句话**：性能那条是硬的（有官方阈值可对）；平衡那条是"两套独立算法互证"（够硬）；
> 战术那条是分布证据（中等硬）；**评分表是软的，不该被当成"行业标准"。**

## 7. 结论：我的可信度应该怎么算

- **运维/性能类结论**：置信度高。有官方阈值 + 黑盒复现 + 修复前后对照。
- **数值平衡类结论**：置信度中高。两套独立实现互证（10.9 倍 / 11 倍），但"该不该这样"仍是设计判断。
- **玩法深度类结论**：置信度中。分布证据支持"多数局面无感"，但**不支持**"机制无效"。
- **评分与排名**：置信度低。那是我的主观排序，本文之后不再作为结论引用。
