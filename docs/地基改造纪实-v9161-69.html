二、地基：从「18 个手写顺序」到「一张依赖图」

加载方式的变化

data.js→ state.js→ systems.js→ domain.js→ …共 18 个…→ main.js
vendor/three.min.js+ js/bundle.js （由 main.js 的 import 图确定性拼接）
指标改造前改造后收益
HTML 脚本标签182顺序由 import 图决定，不再靠人
依赖声明注释 + 隐式顺序显式 import可静态分析、可校验
构建无确定性拼接器 + 源码哈希两次构建哈希一致
陈旧保护无bundle.hash 比对改源码忘重建 → 测试立即红
为什么不是一步到位用 ES Module？
file:// 不支持原生 ESM（CORS 拦截），而本项目是纯静态站。 所以采用「源码写 import 声明依赖 → 构建成单个经典脚本」—— 既拿到依赖图，又保持离线可用。

三、State 归属：把「靠自觉」变成「靠结构」

核心问题：状态是一个巨大的扁平可变对象，谁都能改谁。代码注释里满是 「唯一出口」「两处同源」——说明这些规则早就在了，但只靠纪律。 归属化 = 把纪律变成结构：写错入口 = 测试红。

三个关键设计

① 原子扣费 take

「不够就整单拒绝，不动任何库存」。 旧写法是先扣再判，容易出现「扣了一半才发现不足」的中间态。

② 下界恒 0

sub 对资源/兵/物品统一封底。 修掉裸 -= 写出负兵 / 负库存的口子（界面显示负数、校验错乱）。

③ 原子占位 claim

英雄「空闲才能占」。老板 v91.45 立的 「同一英雄只能执行一种派遣」，从7 处手写分支收敛为一个判据。

④ 不变量

city.checkInvariants() 五条：兵力非负 · 资源非负 · 格数 48 · 坐标界内 · 当前城必须在当前分片。

四、守卫体系：让规则不会退化

重构最大的风险不是「改错」，是「以后又被改回去」。 每收口一片，就加一条源码级 lint 守卫：

7 条守卫：零裸写 s.items · 零裸改 s.inventory · 零裸改 g.status · 零裸写城市资源 · 零裸改队列 · 零裸改城兵 · 动态键正确性（防字面量键回归）。
覆盖写点：62 + 20 + 16 + 29 + 18 + 38 = 183 处 全部走唯一出口

五、过程中的事故（必须记录）

批量正则把动态键写成了字面量。
把 city.army[k] = (city.army[k]||0)+n 批量改成 armyAdd(city, { k: n }) —— 键名 k 变成了字符串 "k"， 25 处全军覆没，后果是兵种数量静默算错。

是测试网救的：smoke 一次报出 10 条红（军账守恒 / 驻军兵不丢 / 治疗归队 / 解散 / 行军折返）。逐个改成计算属性名 [k] 后全绿。
教训已入档：键名是变量的改动，禁止正则批量，手工逐处 + 改完立刻跑 smoke。

「行为零变化」是什么意思？
所有改动都是把等价写法统一到唯一出口——没有新增玩法、没有调整数值、 没有改 UI。存档字段一个没动，老档直接可读。 这也是为什么三件套能全程保持绿：测试断言的就是原行为。

七、没做什么（明确边界）

  • 没拆 ui.js（1.1MB 巨石）—— 第 1 期只建依赖图，不搬成员
  • 没做真 ES Module 运行时 —— 纯静态站 `file://` 不支持
  • 没动 State 的存储结构 —— 归属的是「怎么写」，不是「存哪」
  • 没修那个已知的种子错配 bug（newGame 的 ensure 早于 state 赋值）—— 修了会移动地形、波及大量布局断言，已记录待单独一轮
