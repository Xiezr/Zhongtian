### 2.2 P0-1：前传首小时卡死（性能护栏测错了对象）

**实测（真实 Chromium + 真实点击）**

```
前传「清剿」一次点击：10,373ms（含 3.2s 等待）→ 同步阻塞 ≈ 7,173ms
GAME.refreshAll()：2,511ms
ui.setView('city')（前传态）：2,377ms
  ├─ SP.distOf 调用 3,712 次 · 耗时 2,363ms
  └─ CDP 剖析：hexDist 87.3%（68.0% + 19.3% 两处）
调用链：ui.setView → ui.renderView → P.syncScreen → P.screenHTML → P.spots → SP.distOf → hexDist(BFS 40,962 格)
```

**根因**（`js/prologue.js:128`）

```js
var tries = d.samples || 4000;
for (var i = 0; i < tries && out.length < lim * 4; i++) {
  ...
  var dist = sp.distOf ? sp.distOf({ci: fromCi}, {ci: ci}) : 99;   // ← 每次一次全图 BFS
}
```

注释写着「球面没有"半径内枚举"的出口，所以抽样 + 按距离筛」——但**该出口存在**：`SP.hopsWithin(ci, hops)`（`sphere.js:477`）就是"单次 BFS 返回半径内全部格"。用 4,000 次 BFS 去模拟 1 次 BFS，复杂度从 O(n) 变成 O(n²)。

**为什么门禁没拦住**：`smoke` 的性能护栏只量 `tickOnce < 6ms`（逻辑层），**没有任何一条断言量 UI 渲染路径**。这是"护栏覆盖错了对象"的典型——绿灯证明的是没被检查的那部分。

**修复（预计 0.5 天，风险低）**

```js
// P.spots：一次 BFS 拿到半径内全部格，再按"有荒野事"过滤
var ring = sp.hopsWithin(fromCi, rad);          // 单次 O(visited)
for (var i = 0; i < ring.length && out.length < lim * 4; i++) {
  var ci = ring[i], dist = sp.distOf({ci: fromCi}, {ci: ci});   // 仅候选格，数量级从 4000 → 数十
  ...
}
```

验收建议：新增一条**渲染路径**性能断言（前传态 `P.screenHTML()` < 50ms + `refreshAll()` < 100ms），否则同类问题三个月后照样复发。

## 3. 游戏性维度

### 3.1 核心循环是完整的，内容量是真的

`前传打野 → Lv20 建城 → 建设/募兵 → 出征占野地 → 升将强化 → 打更高级野地 → 名城 → 星球 → 空间站/舰队`，每一环都有产出，且**反馈层做得非常厚**：战报、沙盘逐帧回放、逐条淡入、前传四档试炼、集市行情、换季大集、路上事件三选一、村社、四方势力、竞争者 AI、遗迹、奇观。

这套东西在同类里属于"内容密度上乘"。问题不在"有没有"，在**玩家的每一次点击有多少决策含金量**。

### 3.2 战术层：实测为"假深度"（P0-3 证据）

**（1）动作三角：两个动作严格劣**

同一场 Lv8 重甲样本（守军 7,900，我方 4,380，默认胜）：

| 动作 | 回合 | 结果 | 我方损失 | 相对基准 |
|---|---|---|---|---|
| 全前进 | 7 | 胜 | **181** | — |
| 全体固守 | **30（撞上限）** | 胜 | **1,109** | **+513%** |
| 仅近战固守 | 30 | 胜 | 1,115 | +516% |
| 全体后退 | 21 | 胜 | 25 | 小样本局 |

旧版"全体守住把战损从 53.6% 压到 4.4%"的霸权已被修掉（v91.95 动作三角），但**修成了反向霸权**：固守不再减伤到划算，而是拖长战斗 → 多挨打。三选一里有一个是正的、两个是负的，玩家不需要思考。

**（2）选靶：七个目标，六个数一样**

同一场，逐一把"打谁"指定为不同兵种：

```
集火 步行机/盾卫/自走火炮/伏击车/电磁盾卫/无人轰炸机 → 损 216（六个完全相同）
集火 主战机甲（=默认目标）                          → 损 181
```

也就是说：**指定目标的最好结果就是"不指定"**。v89.192 修了"射程外仍传 preferId"的 bug，但目标选择依然没有产生任何正期望差异——面板上的"目标"下拉是纯装饰。

**（3）默认托管**：`settings.smartBattle` 默认开（`data.js:1257`），绝大多数玩家根本不会打开战术面板，AI 替他们决定。

> 对照行业：率土/三战固定 8 回合，动作（防御/突击/迂回）有明确克制环与正期望窗口；Into the Breach 每个动作都可预测、每个回合都必须做取舍。本项目的动作没有"什么时候该固守"的答案，所以它不构成策略。

```
纯轨道炮 7胜0负 · 轨道+步 6-1 · 纯重机枪 5-2 · 电磁盾+主攻 4-3 · …
泰坦+东风 1-6 · 盾卫掩护东风 3-4 · 步坦炮混编 2-5
```

玩家把科技、建筑、资源投到"高阶兵种"上，换来的是**更差的性价比**。这不是"难度曲线"，是**奖励反向**：越晚期的选择越亏。设计与代码里对"梯级质变"的追求（装备 2.5→1.7 递减倍率是健康的），在兵种这一层完全没有兑现。

> 唯一可能的辩护是"训练时间"（东风 1800s vs 轨道炮 260s）——但在一款有并行队列、挂机产出、离线补算的游戏里，时间是最不缺的资源。而且即便是纯 1v1 而非混合编成，结论也不变。

### 3.4 战力口径不能当胜负依据

UI 里有「⚖ 战力评估」（v91.84）。实测它的判别力：

- 同军资 91 组里，**战力高者胜 78 组（86%）**——作为粗筛可以；
- 但**同"战力 1.15 倍"下，编成质量让损失从 11% 变到 48%（4 倍差）**：

| 编成（战力均 = 守军 ×1.15） | 兵力 | 回合 | 我损 |
|---|---|---|---|
| 全泰坦 | 142,592 | 7 | **11%** |
| 标准混编 | 308,651 | 9 | 19% |
| 远程炮阵 | 165,230 | 7 | 26% |
| 重甲机甲 | 131,547 | 7 | 29% |
| 轻步兵为主 | 498,294 | 9 | **48%** |

- 等级曲线在高端**非单调**：Lv13 损 84%、**Lv14 全灭（100%）**、Lv15 反而 43% 获胜。战力 1.15 倍照样团灭。

结论：面板上的"战力"只能告诉你"大概能不能打"，不能告诉你"这场会不会全灭"。玩家最需要的信息（我该带多少兵）恰恰是它给不了的。

### 3.5 成长节奏

| 项 | 实测 | 判断 |
|---|---|---|
| 战斗回合 | 中位 **9**，区间 5~17（旧总评：中位 4） | **明显改善**，战术空间变厚；30 回合上限仍未被用满 |
| 经验曲线 | α=1.25；累计占比 Lv100 **14.0%** / Lv200 **66.4%** | 仍然后置（旧总评同值）；但战斗/练功走"相对口径"（占比式），曲线只影响绝对经验来源，实际影响被绕开 |
| 建造时间 | 12 级循环 · 单次 ≤24h | 合理，已按老板口径重设 |
| 前传 | Lv1→20 约 **9 场**试炼 | 节奏清爽，是好的 FTUE 设计（但被 P0-1 的卡顿毁掉） |

### 3.6 目标与留存

- **有终局选择，没有胜利条件**：`ending.js` 的"接进去 / 关灯"是全局唯一一次不可撤销选择，两个选项都付代价（+35% 产出 vs 永久锁死惰性 / −10% 产出 vs 能力上限打开）。这是**设计水平很高的一段**——但它不是"目标"，玩家没有"我赢了"的那一刻。
- 目标句/里程碑只覆盖探索（迷雾探明度），没有"阶段目标 → 完成"的显式推进感。
- 世界是活的（village / rival / faction / events / 集市换季），这点比旧总评时好很多：世界不再只是背景板。

## 7. 诚实缺口（我没能验证的）

1. **无人类试玩**：所有玩法结论来自引擎实测与代码阅读，没有真人 30 分钟上手录像；"玩起来闷"这类判断我无法量化。
2. **单 seed**：野地守军按 (格, 日期) 生成，我只测了一个 seed/日期；`Lv14 全灭` 可能是当日守军构成导致，不排除换日恢复。
3. **无真实显卡**：headless Chromium 无 GPU，但 `hexDist` 是纯 CPU 运算，性能结论不受影响；渲染类帧率未测。
4. **未审的层**：3D 星球渲染（three.js）、AI 生成素材的版权与一致性、存档跨版本兼容矩阵（只抽查了校验逻辑，没跑 4,394 份历史存档）。
5. **"行业最高标准"的边界**：本报告按商业单机发行基线评分；若定位是"自娱/小众硬核"，§2 与 §3 的多条扣分会显著减轻（例如 a11y、资产体积、胜利条件）。
6. **审核本身的一个教训**：我第一版用"固定兵力配比"测等级曲线，得出 Lv9~15 全灭的错误结论——原因是 `power.armyOf` 时**没把守将传进去**。修正后（含守将）Lv10 在 1.15 倍战力下全部编成可胜。这条要写下来，因为它正是"探针口径不对会导出完全相反的结论"的实例。
