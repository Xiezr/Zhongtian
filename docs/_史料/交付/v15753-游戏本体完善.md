## 六、§十四 的解释（本轮只解释，未改一字）

一句话：**门禁是机器铺满的地板，不是天花板** —— 它能证明「代码做了你说的」，
证明不了「你说的是对的」。AI 把「写错代码」的成本压到近零，却把「写错题目」的成本放大了。

| 层 | 管什么 | 谁判 | 卡不卡 |
|---|---|---|---|
| L1 地板 | 类型/编译/lint/确定性单测/体系自洽 | 机器 | **卡死** |
| L2 趋势 | 覆盖率/复杂度/变异测试/视觉基线 | 机器出报告 | **不卡** |
| L3 判断 | 需求真被满足没 / 边界 / 耦合 / 业务正确性 | **人** | 不设为门禁 |

配套四条：① 意图校验四段对账链 `老板原话 → 交付附件 → 验证段 → 段号真的在测试里`；
② 独立复核通道（实现 → 另一上下文只读复核 → 人终审）；③ review 专查「平凡解」，
禁止为过闸写 trivial 测试；④ §14.5 写死防自我膨胀：**不新增 Q / 门禁项 / 断言 / 阈值**，
本节只改人的时间分配与复核顺序，且自承「拿不出执行痕迹就是注脚，应当删掉」。

**它现在的执行样本有 3 个**：v157.52 的 diff 复核（抓出对账工具 v1 的空数据平凡解）、
本轮第一次 diff 复核（确认产物同步、无白改）、**本轮第二次只读复核 —— 专审「断言重写有没有偷偷放宽」**
（抓出空对象平凡解、两条 `data-*` 正则可分别命中不同位置、断言分档表未重生成三处，均已当场补，
详见「验证补记」）。§14.5 写死「不新增 Q / 门禁项 / 阈值」依然成立：本轮那两条 smoke 断言
是项目铁律 §0.7「规则变更必须重写旧断言」的产物，不是 §14 带来的新判据。
留 / 精简 / 删仍由老板定。

## 七、索引审核结论（大白话）

`README_INDEX.md` 现在 **8627 行**，其中 **843 行**写的是
`.workbuddy/tools/gltf/node_modules/` 里的**第三方依赖包**（61MB 的 gltf 工具依赖树）。
这些不是我们写的工具，是 npm 装进来的库文件，被索引生成器当成「项目工具」列了进去 ——
**翻索引时一大半是噪音**。

- 生成器 `gen_tools_index.py:126` 用 `os.walk(T)` 全量遍历，没有跳过 `node_modules`；
- **旧索引也是 843 条**，所以是**既有问题，不是上一轮整改引入的**；
- 修法很小：遍历时 prune 掉 `node_modules` 目录，重跑生成器，索引会瘦到只剩真工具。

**我的建议（一句话）**：排除 `node_modules`。理由 = 那 843 行不是我们写的工具，
留着只会让翻索引的人多翻一大半废页；风险 = 几乎零，只改生成器 `os.walk` 一处加 prune，
再重跑一次；改完预计索引从 8627 行瘦到约 7784 行。
老板说「采用简单表述来向我确认」——本轮按「审核确认」的要求**没有改**，等您一句话定夺。
