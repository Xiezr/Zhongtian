# 层次与依赖体检（v156.42）

> 老板 2026-11-02：「可见有很多老旧体系下掩埋的问题，按新体系逐一梳理层次，捋清依赖」

## 一、一句话结论

**这个项目的「三层」是打包分组，不是依赖分层。**

`build_bundle.py` 只按 `order` 把文件拼进三个包，**从不校验依赖方向**。
所以 `core → ui` 不是"违规"，是**从来没有这条规则**。

## 二、分层的实况

| 层 | 模块 | 行数 | 说明 |
|---|---|---|---|
| core | 53 | 40,970 | 数据 / 状态 / 规则 / 域 |
| war | 9 | 10,857 | 战斗 / 战术 / 战斗记录 |
| ui | 24 | 33,249 | 界面 24 个文件（原 ui.js 21456 行拆出来的） |

**反向调用：65 条边 / 177 个调用点。**

按性质分：

| 性质 | 调用点 | 含义 |
|---|---|---|
| **compute** | **122（69%）** | **计算函数被放在了上层** —— 真正的问题 |
| open-ui | 22 | core 直接开界面 |
| notify | 18 | core 调 toast/notify（最容易解耦） |
| refresh | 15 | core 要求重画（map3d.rebuild / renderMapCanvas） |

最重的 6 条边：

```
prologue [core] → ui [ui]        31 处   open-ui, notify, compute
battle   [war]  → story [ui]     24 处   全是 compute
state    [core] → battle [war]   17 处   compute
state    [core] → story [ui]     15 处   全是 compute
domain   [core] → ui [ui]        11 处   compute, notify
tactic   [war]  → story [ui]      8 处   compute
```

### 那条最值得说的边：`story.js` 在 ui 包里，但它是规则

`js/story.js`（337 行，天时/天气/故事）被打进 **ui 包**，
却提供 `prodMult`（产量倍率）、`cityDefMult`（城防倍率）、`troopPower`（兵力战力）、
`combatMod`（战斗修正）—— **这些是决定全局数值的规则，不是界面**。

被 `state`（15 次）、`battle`（24 次）、`tactic`（8 次）、`domain`（4 次）调用。

后果：**改一个天气数值系数，在依赖图上等于是"改了 UI"**。

## 三、测试的观察面全在 UI，决策面全在 core

这是比依赖方向更严重的一条。用断言级归属（一条断言对同一文件只计一次）：

| | 条数 |
|---|---|
| 4250 条 check 总数 | 4250 |
| 直接引用 **ui** 模块的断言 | **806** |
| 直接引用 **core** 模块的断言 | **2** |
| 不绑定任何模块（测数据 / DOM / 行为结果） | **3587** |

**core 层几乎没有被"直接"测过** —— 它只被间接执行（走 UI 流程时顺带跑）。

后果很具体：
- core 的规则算错了，现象会出现在 UI 上（"面板数字不对"）；
- 而断言全在 UI 侧，**定位链是"UI 现象 → 追到 core 函数"**，不是"core 函数直接报错"；
- 所以修起来慢，且容易在 UI 层打补丁（掩盖 core 的错）。

## 四、两个口径都不能直接当"改动成本"

我在这一轮踩了自己的坑，记下来免得再犯：

| 口径 | ui-city 的"牵动条数" | 问题 |
|---|---|---|
| 段级（`seg-modules.json` / `impact_of`） | **1694** | 一个 271 条的段里 3 条碰到 ui-city，就把 271 条全算给它 → **虚高约 19 倍** |
| 断言级（`assert_owner.js`） | **87** | 只覆盖 808/4250 = 19% 的断言，其余测行为不绑定文件 → **覆盖不足** |

**结论：「改这个文件要跑多少条」无法事前准确估算。**
根因是 84% 的断言不绑定具体文件 —— 它们断言的是"跑一遍之后的状态"。

这也解释了之前"按需跳段"为什么失败：不是工具不行，是**没有可靠的归属关系可依**。
正确做法是改完跑一遍看哪里红（`smoke_fast` 222 秒），而不是事前估。

## 五、处置优先级（按「投入产出」排）

| 序 | 事项 | 收益 | 风险 | 建议 |
|---|---|---|---|---|
| 1 | 把 `story` 的规则部分（prodMult / cityDefMult / troopPower / combatMod）搬进 core | 切断最重的 war→ui 边（24 处），天气数值改动不再牵动 UI 测试 | 中（4 个调用方，110 处引用） | **单独立项**，不在顺手改的范围 |
| 2 | notify 类 18 处改事件/回调 | 解耦最干净的一类 | 低 | 可选，收益小 |
| 3 | open-ui 22 处（20 处在 prologue）改"返回意图由上层执行" | 序章与 UI 真正分层 | 中（序章零直接覆盖，动了没人守） | 先补序章断言再动 |
| 4 | 给 core 补"直接"的行为断言 | 定位链从"UI 现象"缩到"core 函数" | 低（只加测试） | 优先做，但按停止规则别一次铺开 |
| 5 | 立"core 不得依赖 ui"的规则 | 防止继续恶化 | 高（要先还 70 处债） | **不做**。没还债就立规 = 门禁永远红 |

## 六、这轮落地的三样东西

1. **`.workbuddy/layer-debt.json`**（台账）
   ```bash
   node .workbuddy/tools/prof/layer_debt.js          # 看现状
   node .workbuddy/tools/prof/layer_debt.js --diff   # 新增/还清（有新增就退出码 1）
   node .workbuddy/tools/prof/layer_debt.js --update # 改了代码后重写
   ```
   它不是"违规清单"，是"从来没有规则"的证据。让新增一条、还清一条都可见。

2. **`.workbuddy/tools/prof/assert_owner.js`**（断言级归属）
   ```bash
   node .workbuddy/tools/prof/assert_owner.js          # 哪些文件被多少条断言直接引用
   node .workbuddy/tools/prof/assert_owner.js --layer  # 按层汇总
   ```
   用来纠正"段级口径虚高 19 倍"的问题。

3. **`js/modules.json` 加了 `_bundlesAre: "packaging-only"`**
   写进唯一权威清单，防止下次有人看到 core/war/ui 三个词就以为有分层约束。

## 七、这轮没做的事，和为什么

- **没立依赖规则**：要立得先还 70 处债，否则门禁永远红 —— 那就是"合法的红"又回来了，
  正是上一轮刚清掉的东西。
- **没搬 story 的规则**：4 个调用方 110 处引用，属于重构，不属"顺手梳理"。
- **没给 core 补断言**：按 AGENTS 的停止规则，不一次铺开。真要补，从
  "改一次 core 就得靠 UI 现象定位"的那些场景开始，一次一个。

**这份体检的价值不在"发现了 65 条债"，而在把三件事说清楚了**：
分层是名义的、测试的观察面错位、改动成本无法事前估算。
这三条决定了任何"重构计划"该怎么排。
