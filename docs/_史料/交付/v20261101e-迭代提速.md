# 迭代提速：把 22 分钟的反馈环压到 8 分钟（+ 秒级内环）

> 日期：2026-11-01　｜　老板：「现在工作速度太慢了，迭代很艰难，确认原因及解决办法」
> 一句话：**慢的不是算力，是同一颗星球被反复问同样的问题。**

## 一、先取证，不猜

用 `--cpu-prof` 跑 smoke 的前 60 段（15,473 行）做剖面，按"自身耗时"汇总：

| 函数 | 占比 |
|---|---|
| `GAME.cityDist`（内联了 `hexDist` 的 BFS） | **50.3%** |
| `hexDist` | 20.6% |
| `GAME._nearestLandCi` | 9.4% |
| GC | 4.6% |
| `GAME.map._cityCiSet` | 4.5% |
| `SP.distOf` | 4.4% |

关键事实（实测，非推测）：

- smoke 前 60 段：**135 次 `newGame`，但只有 3 个种子**（同一个种子用了 **132 次**）
- `sphere.ensure` 累计只有 **5 秒** —— 球面本身是幂等的，**没有被重复构建**
- 但 `newGame` 累计 **318 秒（占 87%）** —— 钱花在"建城/排 NPC/算距离"这些**每次都重算**的活上
- `hexDist` 是**一次 BFS 且没有缓存**：410 座 NPC 城 × 双重循环 = 十几万次 BFS，问的都是同一颗球

## 二、改了什么

`js/sphere.js` 给 `hexDist` 加**有上限的对距离缓存**（无向 → min/max 归一化键）：

- 命中 O(1)，结果与原来逐位相同（就是同一个 BFS 的答案）
- 超过 60 万条形就整表清空（不做 LRU，峰值内存可控）
- **球面重建时清空**（`build()` 末尾 `_dMemoClear()`）—— 否则旧地形的环数会套到新星球上

## 三、效果（同一台机器，同一份代码除缓存外一字未改）

| 指标 | 改前 | 改后 | 倍数 |
|---|---|---|---|
| smoke 前 60 段（剖面切片） | 362 s | **46.7 s** | 7.8× |
| 其中 `newGame` 累计 | 318 s | **15.4 s** | 20× |
| **smoke 全量** | ~22 min | **462 s（7.7 min）** | ~2.9× |
| **gate.py --full（8 脚本并发）** | ~22 min | **613 s（10.2 min）** | ~2.1× |
| 断言结果 | 4328 通过 / 10 失败 | **4329 通过 / 9 失败** | 一致（少的那条是 hash 假红已修） |

正确性护栏：改动前后跑同一段切片，**2039 条通过 / 2 条失败，失败集合逐条相同**。

## 四、还加了两个工具（这才是"迭代不艰难"的关键）

```bash
# ① 秒级内环：只跑最后几段（§585–§588 = 29 条断言，1.9 秒）
node .workbuddy/tools/prof/smoke_slice.js --from 585
node .tmp_smoke_slice.js

# ② 谁在吃时间：截断剖面 + CPU 火焰图
node .workbuddy/tools/prof/gen_head_prof.js 60
node --cpu-prof --cpu-prof-dir=.workbuddy/tmp/cpuprof .tmp_smoke_head.js
node .workbuddy/tools/prof/top_cpu.js .workbuddy/tmp/cpuprof/*.cpuprofile 20
```

`smoke_slice.js` 的已知边界：切片会跳过前面段的"建世界"，故生成时会先做一次预热
`newGame`；若某条断言仍依赖更早段的顶层声明，它会红 —— **那是切片限制，不是回归**，
照旧跑全量确认。

## 五、下一步（按性价比排序，未做）

1. **e2e 现在是关键路径**（gate 墙钟 613 s ≈ e2e）。同一套 `--cpu-prof` 打一遍，
   极可能还是距离/NPC 排布那几段；`newGame` 缓存对 e2e 同样有效。
2. `_nearestLandCi`（9.4%）：`hopsWithin` 每次 BFS，可加"起点+半径"缓存 ——
   但它返回**数组会被调用方持有**，缓存前必须确认没人改它（有改坏风险，故本期未动）。
3. `_cityCiSet`（4.5%）：签名用 `cs.map(id).join(',')`，410 城 → 每次拼 5KB 字符串；
   可换成增量计数/版本号。
4. **9 条历史红**让门禁永远是红的 —— 每次提交都要人工判断"这 9 条是不是我弄的"，
   这本身就是最大的心理成本。建议二选一：修掉，或建"已知失败基线"让门禁只报**新增**红。
   （这是策略决定，需老板拍板，本期未动。）
5. 分片（把 smoke 切成 8 片并行）**仍不建议**：段间共享顶层声明，
   上次尝试因"模板串/正则骗过词法分析"与 `ReferenceError` 失败；
   当前 7.7 分钟 + 秒级切片已经够用。
