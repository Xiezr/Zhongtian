# 项目索引：从"改一行要猜它在哪"到"指哪打哪"

> 老板 2026-11-01：「我不知道，是否可以建立一个资产链，或者逻辑对应表，或者项目树，或者其他还有助于指哪打哪的方式」
> 一句话：**能。但关键不在"建一张图"，而在"这份清单必须自动生成、被工具消费、且过期会报红"。**

---

## 一、先想清楚：为什么"画一张架构图"没用

上个月画的那种图，三周后一定不准 —— 因为它是**手写**的。
这个项目已经证明过一次：同一个「模块有哪些」的清单，仓库里有 **8 份副本**
（build ORDER / build UI_SPLIT / audit MODULES / audit REF_MODULES / smoke 静态检查 ×2 / smoke hash ORDER ×2），
加一个模块要改 8 处，漏一处就出假红或假绿。

> ui.js 拆分那次，就因为漏了 smoke 里 200+ 处 `readFileSync('js/ui.js')`，
> 断言从 4403 条直接掉到 **3754 通过 / 658 失败**。

所以"指哪打哪"的真正前提是 **单一来源 + 自动生成 + 机器对账**，
不是图形。图只是它的一个视图。

---

## 二、建了什么：一索引 · 一查询 · 一对账

```
js/modules.json                       30.7 KB   ← 权威清单（唯一手改处：layout）
.workbuddy/index/project-index.json   250 KB    ← 查询库（符号/断言/资产/引用）
        ↑ 由 gen_index.js 自动生成
.workbuddy/tools/map/gen_index.js               ← 生成器（扫源码，不读缓存）
.workbuddy/tools/map/who.js                     ← 查询器（只读）
        ↑ 消费者
.workbuddy/tools/patch/build_bundle.py          ← 构建从这里读 ORDER（已切换）
audit.js                                        ← 死函数/引用检查从这里读（已切换）
smoke §591（5 条）                              ← 过期或抄回清单就报红
```

### 索引里有什么

| 维度 | 内容 | 规模 |
|---|---|---|
| 模块 | 名 / 文件 / 行数 / 分包 / 职责 / 依赖 / 被依赖 | 86 |
| 符号 | `GAME.map3d`、`ui.openDuelPanel`、`SP.cells`… 定义在哪个文件第几行 | 2,295 |
| 断言组 | `§N` → 标题 / 行号 / 条数 / **涉及哪些模块** | 264 组 |
| 资产 | 路径 / 大小 / 类型 / **谁加载它** | 530 个（1,693 MB） |
| 对账 | 各处硬编码清单与权威清单的差异 | 6 处 |

**断言 → 模块**这一条最费工夫，也最值钱：它让"改了 X 要跑哪几条"变成可计算的。
做法是双路匹配 —— 段内直接写的文件名，加上**段内出现的其它模块导出的符号**反查归属。
只走前一条时，`map3d` 报"0 组相关断言"，实际有 16 组。

### 场景 C：改资产时先看资产链

```bash
node .workbuddy/tools/map/who.js --assets            # 六个目录全看
node .workbuddy/tools/map/who.js --assets actors     # 只看一个
```
```
■ assets/actors　4 个 / 6 MB　[glb×2 js×2]
　　加载方：js/gltf.js　（目录级：代码用拼路径，抓不到文件名）
■ assets/icons　357 个 / 683 MB　[png×244 jpeg×113]
　　加载方：js/bitmaps.js, js/ui-planet.js
■ assets/mecha_raw　25 个 / 72 MB　[png×23 jpeg×2]
　　加载方：（未在代码里找到引用 —— 可能是未用资产）
■ assets/wonders　27 个 / 881 MB　[glb×18 js×9]
　　加载方：js/map3d.js　（目录级：代码用拼路径，抓不到文件名）
```

> `.glb` 与 `.glb.js`（base64 镜像）会同时列出 —— 它们是**同一份资产**的两种形态，
> 不是两套。改模型时两个都要重新生成。
>
> 顺带发现：`assets/mecha_raw`（72 MB）**没有任何代码引用**，像是处理前的原始素材。
> 删不删是老板的决定，索引只负责把它显出来。

反方向更常用：**改代码时要知道它管哪些资产**。

```bash
node .workbuddy/tools/map/who.js --impact gltf
```
```
　◆ 相关资产（目录级：代码用拼路径，按目录算）assets/actors
　◆ 角色标定表 GTF.FIT（改模型/改尺寸要一起改这里）：
　　　Soldier           scale=69.0　stand=[90, 0, 0]　footY=0
　　　RobotExpressive   scale=0.2201　stand=[0, 0, 0]　footY=0
```

**为什么要分"文件级"和"目录级"**：`gltf.js` 里写的是
`'assets/actors/' + name + '.glb'`，源码里根本没有 `Soldier.glb` 这个字面量，
文件级匹配全部落空 —— 一个资产都不显示，而这恰恰是"加载全部角色模型"的那个模块。
所以目录级引用不是可有可无，它是**拼路径写法的唯一可见线索**。

**标定表**是资产链上最容易漏的一环：换一个角色模型，除了换文件，还要改
`js/gltf.js` 里的 `GTF.FIT`（缩放 / 立姿角 / 贴地补偿）。光看 `assets/` 目录永远看不见这条关系。
`--impact gltf` 会把它直接列出来。

## 四、怎么保证它不会变成第 9 份废纸

三条，缺一不可（缺任何一条，索引就会退化成一个没人信的快照）：

1. **构建真的从它读**。`build_bundle.py` 里的 `ORDER/WAR/UI_SPLIT` 已删除，
   改成 `_load_layout()` 读 `js/modules.json` 的 `layout`。
   迁移后重建，hash 与改前**完全一致**（`21e405079f05b43a`），产物字节数也没变 —— 证明搬运无损。

2. **audit 也真的从它读**。`MODULES` / `REF_MODULES` 改成 `require('./js/modules.json').order`。

3. **过期会报红**（smoke §591，5 条）：

| 断言 | 守什么 |
|---|---|
| ① 清单存在且带 layout | 生成器没跑过 |
| ② layout.order 与磁盘双向相等（且 ≥50） | 漏一个不进 bundle（假绿）/ 多一个构建就炸（假红） |
| ③ 分包不重不漏 | 同一模块被打进两个包，后加载的会覆盖前者 |
| ④ **sourceHash == 当前源码重算值** | 改了源码没重跑索引 —— 此时 who.js 在骗人 |
| ⑤ 构建/审计不再自带清单 | 有人图省事又抄了一份数组，索引当场退化成第 9 份 |

第 ④ 条是踩过坑才写对的，见下。

## 五、三个坑（都是"看起来对、实际是错的"）

### ① 依赖图全连接：统计粒度选错，图就废了

第一版统计"模块里出现了别的模块导出的任何符号"，于是 `GAME.newGame()` 这类**顶层函数调用**
也被算成"依赖 domain"，结果每个模块都依赖 80+ 个模块 —— 图上全连，等于没图。

正解：只认两种真依赖 ——
`GAME.<ns>.xxx`（二层访问，ns 是被当命名空间用的）与 `ui.fn / DATA.x / SP.x` 的符号级归属。
顶层函数调用不计入模块边界。改完 map3d 的依赖从 82 降到 24，被依赖从 0 变成 9。

### ② 平凡解：比较两个陈旧值，只能证明"它们一样旧"

§591④ 第一版写的是 `MD.sourceHash === bundle.hash`。实测故意改一个字、既不重跑索引也不重新构建 —— **它照样绿**。
因为两个都是上一次的快照。正确判据必须引入**外部真值**：拿当前源码现场重算一遍。

> 实测：改 `fog.js` 加一行注释 → `index=21e405079f05b43a now=ecdceb629db20eb6` → 红，并直接给出修复命令。

### ③ 循环依赖：清单要读构建脚本，构建脚本又要读清单

如果"生成器从 build_bundle.py 读 ORDER、构建从 modules.json 读 ORDER"，就成环了。
打破方式：**layout 只在首次迁移时来自构建脚本**，之后一律以 `js/modules.json` 为准，
构建脚本反过来读它。（`_layoutFrom` 字段会写明这次用的是哪一份。）

## 六、它顺手抓到的真问题

**`audit.js` 的死函数检查一直漏掉 6 个模块**：
`gltf / bitmaps / gicons / portraits / tactic`（`MODULES` 里没有）。

也就是说这 6 个模块的函数**从来没被死函数检查扫过**。
改成从 `modules.json` 读之后：扫描函数数 **2200 → 2520**，死函数仍为 0，未定义引用归 0
（之前那条 `GAME.gltf.*` 的假红也一并消失）。

> 这就是"单一来源"的直接收益：不是"更整齐"，是**扫到了以前扫不到的地方**。

## 七、以后怎么维护（三条规矩）

1. **加模块**：新建 `js/x.js` → 在 `js/modules.json` 的 `layout.order` 插一行 → 跑
   `node .workbuddy/tools/map/gen_index.js` → 构建。
   **别再往 build_bundle.py / audit.js / smoke 里加数组**（§591⑤ 会拦）。
2. **改完源码**：跑一次 `gen_index.js`（它会同时刷新 `sourceHash`），否则 §591④ 红。
   只想核对不改盘：`node .workbuddy/tools/map/gen_index.js --check`。
3. **找东西**：先 `who.js <关键词>`，不要一上来 grep —— grep 只会给你 200 行，
   who.js 会告诉你"这属于哪个模块、波及哪 16 组断言、下一步跑什么"。

## 八、诚实缺口

1. **资产引用是"路径或文件名子串"匹配**，同名文件可能误报（如多处 `pool/`）。
   真正的沙箱级确认还得靠 `--impact` 看具体模块。
2. **`project-index.json` 不进 git**（250KB + 带时间戳，每天刷无意义 diff），
   新克隆要跑一次生成器；`who.js` 会在缺文件时直接提示命令。
3. **依赖是"静态文本引用"**，不是运行时真实调用图 —— 反射式调用
   （`ui['open' + x]`）抓不到。这类在本项目里很少，但存在。
4. **断言归属是启发式**：靠"段内提到了该模块的文件名或导出符号"。
   跨段共享状态的断言可能归到多个模块，我按"都算"处理，不追求唯一。
5. **未做真机验证**：以上全部是 node 侧行为，`who.js` 的输出格式没有 UI 化。
   要不要做一个可视化面板（点模块看依赖图），等你决定 —— 现在命令行够用，做面板会引入新的维护面。

## 九、补记：这次改造连着的两个"假红/假绿"

### ① 假绿：audit 一直漏扫 6 个模块（真问题）

`audit.js` 的 `MODULES` 手抄数组里少了 `gltf / bitmaps / gicons / portraits / tactic`。
后果是这 6 个模块的几千行代码**从来没进过死函数扫描**。
改成读 `modules.json` 后：扫描函数 **2200 → 2520**，未定义引用归 0（原先那条 `GAME.gltf.*` 的假红一并消失）。

### ② 假红：补扫之后撞出来的"重复定义"

`⚠ sc.onload ← gltf, map3d`

这不是 bug：`sc` 是两个文件里各自的 `document.createElement('script')` 局部变量。
audit 原来的判据是"全名相同即重复"，但**各模块开头的别名**（`var S = GAME.state`、
`var M = GAME.map3d`）本来就跨文件重名 —— 那是设计，不是覆盖。

修正判据：**只对跨文件的全局命名空间判重**（`GAME / DATA / SP / ui / F / U`）。
文件内别名（`S/P/M/T/FA/…`）不参与。修完四项归零。

> 这两个连在一起看才有意思：**假绿（漏扫）被修掉之后，必然冒出一批假红（判据太宽）。**
> 所以"提高覆盖率"和"校准判据"必须同时做，只做前一半会得到一堆噪声，
> 只做后一半则永远看不见漏掉的那 6 个模块。
