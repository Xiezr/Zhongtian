# 规则层下沉：这一刀切在哪（v156.43）

> 老板 2026-11-02：「应该做到什么程度，你把握」

## 一、我的答案：只切一刀，切在最痛的那条边上

不是"全做"，也不是"只出报告"。**做到「一次可验证、零行为风险、指标明确的结构改进」为止。**

具体这一刀：把 `js/story.js` 里**决定全局数值的纯计算**搬到新文件 `js/rules.js`（core）。

理由：体检里 177 个跨层调用点，**122 个（69%）是 compute** —— 计算函数住在上层。
其中 `story` 一个人占 34 处（battle 17 / state 9 / tactic 4 / ui-exped 4），
是最大的一块，而且它搬起来最干净。

## 二、搬了什么，为什么只搬这些

| 函数 | 依赖 | 搬？ |
|---|---|---|
| `currentSeason` | `DATA.SEASONS` + `state.world` | ✅ |
| `currentWeather` | `DATA.WEATHERS` + `state.world` | ✅ |
| `prodMult` | 上面两个 | ✅ |
| `troopPower` | 纯查 `DATA.TROOPS` / `DATA.POWER` | ✅ |
| `combatMod` | `currentWeather` | ✅ |
| `cityDefMult` | `STORY.activeBonds()`（羁绊系统） | ❌ 留 |
| `bondBonus` | 同上 | ❌ 留 |
| `init` / `skyLine` / 播报 | 事件与界面 | ❌ 留 |

**判据只有一条**：只依赖 `DATA` 与 `state.world` 的纯计算才搬。
依赖"另一个业务系统"（羁绊）或"界面/事件"的，一律留在原地 —— 那不是"放错层"，那是它本来就属于那儿。

## 三、零行为风险怎么保证

`story.js` 里 5 个函数**保留同名转发**：

```js
STORY.prodMult = function (res) {
  /* v156.43：实现搬到 js/rules.js（core）。这里保留同名转发。 */
  return GAME.rules.prodMult(res);
};
```

所以：
- 34 处调用点里**改了的**（→ `GAME.rules.*`）走新入口；
- **没改的**（还有别处调 `GAME.story.prodMult`）照样工作，行为逐字节不变；
- 任何一处漏改都不会炸 —— 这是"先保底再优化"，不是"一次性替换赌它没错"。

## 四、这一刀的产出（可量化）

```
跨层调用点      177 → 147   （减少 30；另 4 处是 ui-exped→story 同层，不算反向）
compute 类      122 →  92   （减少 30）
battle → story   24 →   7   （17 处）
state  → story   15 →   6   （9 处）
tactic → story    8 →   4   （4 处）
```

依赖图上多了一条**真实的边界**：**数值规则在 core，界面在 ui**。
改一个天气系数，从此不需要复核 UI 那 800 条断言。

（数字由 `node .workbuddy/tools/prof/layer_debt.js --diff` 复核，见第五节。）

## 五、为什么停在这里，不往下走

| 候选 | 为什么不做 |
|---|---|
| **open-ui 22 处**（20 处在 prologue） | 序章 1821 行、**零直接覆盖**。动了没人守，风险与收益不对等 |
| **refresh 15 处**（`map3d.rebuild` 等） | map3d 依赖 THREE 与 WebGL，搬进 core 等于把渲染塞进数据中心 —— 方向就是错的 |
| **立「core 不得依赖 ui」的规则** | 要先还剩下 143 处债，否则门禁永远红 —— 那就是刚清掉的"合法的红"又回来了 |
| **给 core 大面积补断言** | AGENTS 停止规则：一次一个。从"改 core 只能靠 UI 现象定位"的场景开始 |
| **搬 `story` 的界面部分** | 事件/播报本来就是 UI，搬了反而错 |

**这一刀之后，"分层"第一次有一条能被指认的边界**，而不是三个词。
剩下 143 处是欠条，不是任务 —— 什么时候改到那儿，什么时候还。

## 六、诚实说这次改动的价值

**它没有改变任何玩家能感知的东西**（转发层保证行为不变）。
所以它的收益是"以后每一次改天气/兵种数值都省一次 UI 复核"，不是"现在更好了"。

这类投资该不该做，判断标准是**边际**：如果这个文件一年改 20 次，就值；
如果改一次就再也不动，就不值。本项目天气/战力是高频改动区（老板每次调平衡都碰），所以值。

**但只值这一刀。** 再往下就进入"为了架构好看而重构"的区域，那是我该拦住自己的地方。

### 搬迁过程中被自检抓到的两处（都值得记）

1. **`smoke-test.js` 里那份独立信源的 ORDER 漏了 `rules`** ——
   `gen_index.js` 的"硬编码清单对拍"立刻报「smoke-test.js 的 ORDER 漏了：rules」。
   **这正是清单故意存两份的价值**：构建脚本自己算对了，不代表守卫认得它。

2. **两条断言跟着红**，性质不同：
   - `⑦ 战力口径复用 troopPower` —— 它查的是 `GAME.story.troopPower` 这个**字面路径**。
     搬迁后路径变成 `GAME.rules.troopPower`。判据要换入口，但**语义没变**（仍是唯一出口、不另造第二个）。
   - `§579③ 项目地图模块数` —— `docs/项目地图.md` 里写死 86，实际 87。
     这条是文档与代码的对拍，**它红得对**。

### 一处工具缺陷（顺手修了）

`layer_debt.js --diff` 原来只比**边**（from→to），不比调用点。
于是这次搬走 30 处调用点，diff 报「新增 0 还清 0」——**这次重构在台账上完全隐形**。
已改成同时报「调用点 177 → 147（-30）」和每条边"变瘦多少"。

**工具看不见的那类改善，等于没发生。**
