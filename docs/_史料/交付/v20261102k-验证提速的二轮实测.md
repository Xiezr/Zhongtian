# 验证提速·第二轮：三个假设全被实测否掉

> 老板 2026-11-02：「确认最优了吗，不只是当下最优，而是适应当下及后续任务的最优」

这一轮我试了三个方向，**全部被自己的实测否掉**，其中一个还改了代码又被回滚。
把过程写下来，因为"试过什么、为什么不灵"本身就是结论。

## 一、尝试一：按影响面切片（工具早就存在）

项目里有 `smoke_slice.js`（v156.26 建的），`who.js --impact` 甚至直接建议用它。
实测 `--changed js/ui-space.js`：

```
符号 82 个（有区分度） · 命中 150/238 段
✗ 命中 150/238 段（>50%）—— 影响面太大，跑全量更省时间。
```

**为什么不行**：`ui-space` 里的符号（`setView` / `escape` / `numText` / `TROOPS`）被到处引用，
文本命中法必然放大。之前 map3d 也是 165/238（69%）。

> 这不是工具不好，是**模块耦合度**决定的：任何 UI 改动都"看起来影响一切"。

## 二、尝试二：CPU 火焰采样定位热点

`node --cpu-prof` 跑全量（7 分 54 秒，264010 个采样），按 self time 排：

| 函数 | self | 几乎全部来自 |
|---|---|---|
| **`GAME.cityDist`** | **23.4%** | `pickStartPos → stateOfCity`（99.8%） |
| **`GAME._nearestLandCi`** | **12.1%** | `_relocateNpcSites ← buildNpcCities ← map.generate`（99.9%） |
| `build`（球面构建） | 8.6% | `SP.ensure ← newGame` |
| *垃圾回收* | 7.6% | — |
| `n3` / `h3`（噪声） | 13.6% | 地形 |
| `hexDist` | 7.1% | 距离 |
| `GAME.map._cityCiSet` | 6.1% | `terrainAt ← heightAt` |

**两个真正的病灶，而且都极其具体**：

1. `pickStartPos` 选出生点时，对每个候选格调 `stateOfCity`，里面**遍历所有城算球面距离**
   → O(候选格 × 城数)，吃掉 23%；
2. `_relocateNpcSites` 把每座 NPC 城挪到最近陆地 → 逐城搜索，吃掉 12%。

两者都是"每次都从零算一遍"的 O(n²)，**与地图种子无关**。

## 三、尝试三：固定测试种子（改了代码，零收益，**已回滚**）

想法：398 次 `newGame` 里有 **235 次没传 mapSeed** → 走时间戳 → 每次新 seed → 每次重建。
探针实测：同 seed 第二次起 **15~18ms**，换 seed **675~2425ms（平均 1471ms）**。
按这个算，235 次能省 ~300 秒。

于是给 `newGame` 加了 `GAME.__testSeed`，全量实测：

```
改前 466.8 秒  →  改后 469 秒   （零收益，断言仍是 4418/9）
```

**为什么零收益**：那 1.4 秒里，球面重建只占一部分（8.6%），大头是上面那两个
**与 seed 无关的 O(n²)** —— 换个 seed 它们照跑，固定 seed 也照跑。

已完整回滚（`js/state.js` + `smoke-test.js` 各留一条说明注释），**不留"看起来有用"的开关**。

## 四、还剩下的唯一一条，以及为什么不该做

要动就动算法：

| 优化 | 预估收益 | 成本 | 风险 |
|---|---|---|---|
| `pickStartPos` 距离预筛（先按行政区/粗网格筛城） | ~15% | 3~4 h | **会改变出生点** → 地图布局变 → 几十条断言要重定 |
| `_relocateNpcSites` 改多源 BFS（一次洪泛替代逐城搜索） | ~10% | 2~3 h | 可能挪动 NPC 城位置 → 「城随地形走」类断言红 |

合计能省 **~2 分钟**（8 分钟 → 6 分钟），投入 5~7 小时 + 多轮 8 分钟验证，
且**动的是世界生成的核心**（出生点/NPC 城位置是所有地图断言的基准）。

按当前节奏（每轮 1 次验证、每天 10 轮）：

```
省 2 分钟 × 10 轮/天 = 20 分钟/天 ≈ 7 小时/月
投入 6 小时 + 回归风险
```

**回本约一个月**。但赌注是"地图生成不跑偏" —— 而这个项目历史上，
地图/坐标类的问题（一局两套地形、城随地形走、出生州落点）反复出现过。
**为了每月 7 小时去动地图生成的核心，不划算。**

## 五、结论：8 分钟没有便宜的加速空间

三次尝试的净结论：

| 方向 | 结果 |
|---|---|
| 切片/分档 | ✗ 耦合度太高，命中 >50% |
| 优化最慢段 | ✗ 前 10 段只占 41%，且都是"真跑整局" |
| 固定种子 | ✗ 实测零收益，已回滚 |
| 算法级（唯一剩的） | 收益 2 分钟，成本 5~7 小时 + 动地图核心，回本一个月但风险不对等 |

**所以最优不是"让它更快"，而是"让它别挡路"：**

1. **不重复跑** —— 断言写错时别白跑 8 分钟（20 秒本地预验，已进 AGENTS §一.7）；
2. **不干等** —— 8 分钟放后台，同时写文档/打截图/跑探针（改执行顺序，不动代码）；
3. **错了快停** —— `--bail`（读基线排除已知红），把"错了"的代价从 8 分钟压到 1 分钟。

这三条都不改产品代码、零回归风险，且**对后续每一轮都生效**。
