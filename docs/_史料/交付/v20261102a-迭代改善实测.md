# 迭代改善实测：哪些是真改善，哪些不是

> 老板 2026-11-02：「测试是否有根本性的改善」
> 结论先给：**「知道该改哪、波及什么」有根本改善；「改完跑多快」没有。**
> 分片并行实验证明：最快能到 48.7 秒，但**语义不等价**，不能当回归裁判。

---

## 一、怎么测的（不靠自评）

四条独立实验，每条都有可复现的命令：

| # | 实验 | 测什么 |
|---|---|---|
| A | 故意从 `layout.order` 删一个模块 | 清单漂移**多久**能被发现 |
| B | 手工 `grep GAME.fog.` 与索引的依赖列表对账 | 依赖图**准不准** |
| C | `smoke_slice --changed` 跑三类模块 | 按需验证**省不省时间** |
| D | `smoke_parallel` 把 238 段切 4 份并行 | 迭代速度**能不能根本改善** |

---

## 二、A：清单漂移检测 = 2 秒

```bash
# 从 layout.order 删掉 ui-bag（模拟"加/减模块忘了同步"）
node .workbuddy/tools/map/gen_index.js --check
```
```
✗ 磁盘上有但 ORDER 未登记（不会进 bundle）：ui-bag
✗ js/modules.json 已过期（源码变了没重跑生成器）
耗时: 1996 ms
```

**对照**：改之前，这类漏项要么等 smoke 跑到对应段（8 分钟），要么永远发现不了。
实证：`audit.js` 就漏了 6 个模块**好几个月**（见第五节）。

---

## 三、B：依赖图 —— 抓到一个真 bug，修完更准

手工 `grep -l "GAME\.fog\."` 得到 **13 个**模块；索引说 **15 个**。多出来两个：

| 模块 | 索引说依赖 fog | 实际 |
|---|---|---|
| `placement` | ✅ 对 | `var F = GAME.fog;` —— **不带点**，grep 漏了 |
| `ui-view` | ❌ **假阳性** | `var F = GAME.faction;` —— 是 faction 的别名 |

**根因**：`F.` 这种单字母别名在 60+ 个文件里各指不同对象（fog / faction / …），
索引按"符号名"归属，必然串味。

**修法**：先解析**每个文件自己的别名表**（`var X = GAME.<ns>`），再按别名判依赖；
不在别名表里的单字母一律忽略（宁缺勿错）。

**修完验证**：
```
fog 的依赖方：14 个（去掉 ui-view，保留 placement）✓
faction 的依赖方：新增 ui-view ✓
```

> 这是本轮最有价值的一条：**索引自己被实测打了一次脸**。
> 如果没做 B 这个实验，`ui-view 依赖 fog` 这条假信息会一直躺在里面，
> 下次有人改 fog 时被误导去查 ui-view。

## 四、C：按需验证 —— 对叶节点有用，对枢纽没用

```bash
node .workbuddy/tools/prof/smoke_slice.js --changed js/<模块>.js --run
```

| 模块 | 命中段数 | 结果 |
|---|---|---|
| `map3d` | **165 / 238（69%）** | 工具判定"跑全量更省时间"，直接退出 |
| `ui-bag` | **132 / 238（55%）** | 同上 |
| `fog` | 能跑，**16 秒** | 但**跳过 6 段**（依赖在被跳过的段里）→ 不可靠 |

**结论**：这条路在当前架构下走不通。
`map3d` 是枢纽（16 组直接断言 / 29 个模块依赖关系），改它确实牵一发动全身；
`fog` 虽然小，但按影响面选段会切断 IIFE 边界，跳段后结论不可信。

**唯一能放心用的是"最近几段"模式**：`--from 585` 跑 §585–591（54 条，1.9 秒）——
它只覆盖"我刚写的新断言"，不是回归。

## 五、D：分片并行 —— 技术上半成，语义上不成

工具：`.workbuddy/tools/prof/smoke_parallel.js`（把 238 段按区间切 N 份，每份带公共前置，并行跑后汇总）。

### 四轮迭代（每轮都是被上一轮的失败推着走的）

| 轮次 | 做法 | 结果 | 崩在哪 |
|---|---|---|---|
| 1 | 裸切 4 份 | **4 份全崩，0.2 秒** | `Cannot find module './js/bundle-core.js'` —— 分片落在子目录，`__dirname` 变了 |
| 2 | 分片放仓库根 | part1 ✅ 2195/1，其余崩 | `fsMod is not defined`、`DC is not defined` —— 它们是**段内**定义的工具，不在 prelude |
| 3 | 加"公共头"（段 0+1） | part1 ✅ 2105/1，part2/3/4 崩 | `s.ruler` / `st.battles` 读不到 —— **`GAME.state` 是空的** |
| 4 | 每份自带 `newGame` | part1 ✅ 2105/1、part4 ✅ 378/0 | part2 `withoutEncounter is not defined`、part3 `DC is not defined` —— 依赖是**网状**的，不是"前两段就够" |

### 最终数据（第 4 轮）

```
.tmp_par1.js  ✅  2105 通过 / 1 失败
.tmp_par2.js  ✗  ReferenceError: withoutEncounter is not defined
.tmp_par3.js  ✗  ReferenceError: DC is not defined
.tmp_par4.js  ✅   378 通过 / 0 失败

合计 2483 通过 / 1 失败　墙钟 213.9 秒（4 进程）
对照：全量串行 4408 通过 / 9 失败　458 秒
```

### 两个必须说清的问题

**① 少跑了 1925 条断言**（2483 vs 4408）。
不是"跑得快"，是"跑得少"——崩掉的两份里那些断言根本没执行。把它当通过数是自欺。

**② 语义不等价**（更致命）。
全量跑时，后面的段看到的是**被前面段改过的世界**；
分片后每份 `newGame` 都是全新世界。第 4 轮之所以能跑通两份，正是靠这个"重置"，
但它同时改变了断言的前提。**分片结果不能当回归裁判，只能当加速冒烟。**

### 但有一个硬数据值得记住

part1 单独跑 **2105 条只用 48.7 秒**。
说明 458 秒里有 410 秒花在后 2300 条上 —— **耗时分布极不均匀**，
按段数均分是错的分法（应该按实测耗时切）。

## 六、根本症结：smoke 是"一个有状态的剧本"，不是"238 个独立测试"

四轮分片失败，崩点各不相同，但根子是同一个：

> **段与段之间共享一个可变的 `GAME.state`。**

具体形态：
- 段 0/1 定义了 `fsMod / DC / withoutEncounter` 这类工具，后面的段直接用；
- 前面的段 `newGame` 建了世界，后面的段假设世界已存在；
- 中间的段改了世界（打仗、建国、拨钟），后面的段看到的是改后的状态；
- 还有故意的破坏测试（`zz_bad`）留在里面，它依赖前序状态才能正常收场。

所以"切段"必然出事：切哪一刀都会切断某条隐式依赖。

## 七、诚实的结论

### 真改善（可以验、有数字）

| 项 | 改前 | 改后 |
|---|---|---|
| 模块清单 | 8 份副本 | **1 份**（`layout`） |
| 清单漂移检测 | 8 分钟（或永远发现不了） | **2 秒** |
| audit 覆盖率 | 80 模块 / 2,200 函数 | **86 / 2,520** |
| "改这个会影响什么" | 靠记忆 + 全仓 grep | **`who --impact` 一条命令** |
| 依赖图准确性 | 无 | 有，且**本轮实测修掉 1 个假阳性** |

### 没改善（本轮实测证伪）

- **验证时间还是 458 秒**。`--changed` 对 `map3d` / `ui-bag` 这类模块直接放弃，对 `fog` 跳段不可信。
- **分片并行跑不通**：技术上 2/4 成功，语义上不等价，少跑 1925 条断言。

### 一句话

> 这一轮改变的是**「知道」**（知道改哪、知道波及什么、知道清单有没有漏），
> 没有改变**「快」**。而"快"的瓶颈不在工具，在**测试段之间共享可变世界**这个架构债。

## 八、下一步（需要老板拍板选路）

**路线 A：段独立化（根治，成本高）**
给每段加 `resetWorld()` + 只读 fixture，让 238 段变成 238 个独立测试。
做完之后：可按段跑、可跨核并行、红点能精确归因。
可行性已被证明：`newGame` 同 seed 只需 **15ms**，全 238 段各自建世界也就 3.6 秒。
代价：需要逐段改（238 段），且要重跑基线。

**路线 B：按耗时切分（治标，成本低）**
不追求"语义等价"，只把 smoke 切成"快段/慢段"两批，慢段单独跑。
省不了多少（慢段本来就是大头），但能让日常改动的反馈从 8 分钟降到 2~3 分钟。

**路线 C：不动（维持现状）**
458 秒 + 9 条已知失败基线。日常靠 `--from 585` 的 1.9 秒内环 + 提交前全量。

我倾向 **A**，但这不只是一次重构 —— 它要动 4 万行测试代码，
且中途会有大量"这段到底依不依赖前段"的判断。**要不要开，请你定。**
