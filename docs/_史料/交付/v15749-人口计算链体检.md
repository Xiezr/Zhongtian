# v157.49 · 幸存者「很久都不满」——计算链体检与修补

> 老板原话：「人口很久了都没满，什么计算链出了问题，改」
> 结论：**链路上真有一处丢时间的 bug（已修）**；另外 4 个环节逐一量过，口径一致，没问题。
> 补满时长同时从 14 现实小时压到 4 小时（保留稀缺性，但玩家一次会话里看得见进度）。

---

## 一、先说结论

| # | 环节 | 实测 | 判定 |
|---|---|---|---|
| 1 | 每秒推进（`tickOnce`） | 手动 `simulateSeconds(60)` → 增量 = 350/3600×60，**精确** | ✅ 没坏 |
| 2 | 主循环（`loopPulse` → `tickOnce`） | 进游戏后真实跑 20 秒 → 增量 1.944 = 期望 1.944 | ✅ 没坏 |
| 3 | **小缺口（1~5 秒）分支** | 20 拍 × gap=3.4 秒（真实 68 秒）→ 人口增量 **0**，丢失 **100%** | ❌ **真 bug，已修** |
| 4 | 离线补算（`simulateBulk`） | 8 小时离线 → 补齐 8×350，封顶不越界 | ✅ 没坏（v157.14 修过） |
| 5 | 界面读数 | `+350/时`、悬停「基准 4 小时补满」「约 X 时 X 分后补满」 | ✅ 与结算同源 |

**所以"很久没满"= 第 3 条的丢时间 + `fillHours=14` 这个参数太长，两件事叠出来的。**

## 二、第 3 条：怎么丢的（这是真 bug）

`js/state.js` 的 `_gapCatchupOf`（时间推进的唯一出口）旧逻辑：

```js
if (!GAME.state || !(gapSec > gate)) return { mode: 'skip', secReal: 0 };  // gate = 5 秒
```

缺口 ≤ 5 秒时**一秒都不推进**，推进全靠 `main.js` 那一拍 `GAME.tickOnce()` —— 而它**固定只走 1 秒**。

于是：`setInterval(1000)` 名义 1 秒一拍，但主线程一忙（3D 重绘 / 大面板 / 存档），实际可能 2~4 秒才来一拍；
每一拍 gap ∈ (1, 5] 都判 skip → 只走 1 秒 → **真实时间被吞**：

- 间隔 2 秒 → 丢 50%
- 间隔 3.4 秒 → 丢 71%（实测 20 拍 68 秒，人口增量 = **0**）
- 更狠一档：`_vis199 === false`（界面被遮住）时 main 连那一句 tickOnce 都不执行，skip 期间推进 = **0**

因为 `tickOnce` 是全系统唯一的时间刻度（人口 / 资源 / 队列 / 体力都挂在它的 `dtReal = 1` 上），
这一处丢时间 = **全系统一起慢**，玩家最先看出来的就是"人口怎么老不满"。

### 修法

1. `state.js`：小缺口由 `_gapCatchupOf` **按真实缺口逐秒推进**（`simulateSeconds(n)`），
   并用小数累加器 `GAME._loopSkipAcc` 把每拍的零头带到下一拍 —— 长期零漂移（实测 68 秒 → 68 秒，损失 0%）。
2. `main.js`：skip 分支**不再补 tickOnce**（否则双推，人口/资源翻倍）；error 分支保留兜底一拍。

## 三、第 5 条之外：参数从 14 小时 → 4 小时

`DATA.POP_CFG.fillHours` v99 从 2 拉到 14（"人口不该被时间抹平"）。但实机里：

- cap 1400 的城，增速 100 人/时 → 一局 2~3 小时只涨 15%~20%；
- 玩家对人口的唯一读数就是"一直不满"，于是合理怀疑计算链坏了 —— 本轮确实也真查到一处。

改成 **4 小时**：一次会话看得见明显进度、两三次会话补满；打光一支军仍要小半天回血，稀缺性保留。

实测（新开局，cap 1400）：

| 时长 | 人口 | 占上限 |
|---|---|---|
| 1 现实小时 | 350 | 25% |
| 4 现实小时 | 1400 | 100% |

界面文案同步（同一字段读，无第二份）：`幸存者 560 +350/时` · 悬停「基准 4 小时补满 · 约 2 时 24 分后补满」。
