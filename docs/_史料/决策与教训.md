## 九、自我改进的可操作定义

> 老板 2026-11-02：「不断自我改进的完备」

**不是"以后注意"，是把这次的漏法固化成一个每次都会跑的判据。**

本轮三个例子：

| 漏掉的 | 固化成的检查 |
|---|---|
| 6 条断言写死 `true`，永远绿 | Q1 恒真扫描（gate 每轮跑） |
| 公共头 112 条断言在分片里从未执行 | Q3 分片/全量条数比（census 永久记录） |
| 基线 9 条永久免检 | Q2 since + 30 天到期（到期自动红） |

**反例（就在本仓）**：`smoke_fast.js` 曾写着「比串行少 ~116 条属正常」——
它把"少跑了"定义成正常现象，于是再没人问为什么少，112 条断言就这样静默失效。
**任何"这是正常的"注释，都是一个待查的洞。**

配套纪律：
- 发现一个体系的盲区 → **当轮就加检查**，不留 TO-DO；
- 阈值集中在 `tier_audit.js` 的 `LIMIT` 里，且**注明哪些是拍的**（现在 35% / 12 / 20 / 30 天全是拍的，
  等两三版数据再校准 —— 写死一个"精确"的假阈值比不设阈值更会骗人）。

## 十、断言强度：把功能改坏，看它红不红（v156.40）

```bash
node .workbuddy/tools/prof/mutation_probe.js --list          # 看有哪些变异
node .workbuddy/tools/prof/mutation_probe.js --run hpMult:no-bonus
```

原理：**运行时替换**`GAME.*` 上的函数（不改源码，零恢复风险），跑一遍 smoke：
- **killed**（断言红了）= 这个功能有断言守着；
- **survived**（全绿）= 功能改坏了都没人发现，那批断言是装饰品。

实测（2026-11-02）：`hpMult` 恒返回 1 → **8 条断言红**，其中 2 条正是本轮
刚从"恒真"改成真判据的那两条。**这证明改之前它们是装饰品。**

为什么必须做：Q1 的形式扫描（查 `check(名, true)`）只能抓**形式上**的假绿。
断言写得很像样、判据却恒真的那一类，形式检查永远抓不到 —— 只有"把东西改坏"能。

成本：一个变异 3.5 分钟（走分片）。不必每轮跑，**大改前跑一个**即可；
Q1 会盯着 `mutation-log.json`，有 survived 就红、超 30 天没跑就提醒。

## 十一、视觉基线：UI 覆盖，3D 不覆盖（别装）

```bash
node .workbuddy/tools/prof/visual_baseline.js --update   # 存基线
node .workbuddy/tools/prof/visual_baseline.js            # 比对（差异 >0.5% 红）
```

覆盖：顶栏 / 地图底栏 / 城池页（静态、可复现）。
判据：整图差异像素占比，阈值 12/255 过滤抗锯齿噪声。

**3D 不在覆盖范围，理由**：星球每帧都在动（自转 + 海面波浪），
`map3d` 没有时间冻结入口，直接比像素全是误报（同一静止画面连拍两次都能差几个百分点）。
要覆盖得先加 `M.freezeAt(t)` 把 `uTime` 钉死。

⛔ **不许把"3 个 UI 场景"说成"有视觉回归了"**：
「海波太规整」「半径闪烁」两次事故都在 3D，它们现在**依然只能靠人眼**。

## 十二、这套规则自己的停止规则（老板 2026-11-02「跳出技术层面，看看这套规则」）

审计制度有三个已知病理，本仓这套东西**三条都沾**：

| 病理 | 在本书里的样子 |
|---|---|
| **自我膨胀** | 五问 → 六问，只增不减。因为"发现新盲区"永远可能 |
| **目标置换** | 从"保证质量"变成"保证 `tier_audit` 绿"。绿了就等于做好了 |
| **成本外部化** | 跑的时间由使用者付，安心感归规则的作者 |

所以必须有停止条件，否则它会吃掉它要保护的东西：

1. **六问冻结**。不再新增 Q。新发现的盲区只写进文档的「已知盲区」，
   **除非它导致过一次真实事故** —— 那时候再升级成 Q，并说明是哪次事故。
2. **Q6 视觉进观察期**。它到今天为止**没有抓到过一个真问题**（顶栏/底栏/城池三张静态图），
   而它想防的「海波太规整」「半径闪烁」恰恰在 3D —— 它覆盖不到。
   **连续 10 轮没抓到真问题就降级为手动工具**，不再进六问。
3. **判据只留能改行为的**。一条规则如果"违反了也没人受罚、也没人事后追问"，
   它就不是规则，是注脚。
4. **每次加规则前先问**：删掉它，玩家能感知的质量会掉吗？
   答"不会" → 它是仪式，别加。

**这套规则的产出账**（用来定期算它值不值）：

| | v156.39 + v156.40 两轮 |
|---|---|
| 改的产品代码 | **2 行**（`ui.openLandModalCi` 那一处） |
| 抓到的产品 bug | **1 个**（2D 点击无响应 —— 还是我自己上一轮删坏的） |
| 抓到的测试体系 bug | 6 个（恒真断言 / 112 条漏跑 / 基线无期限 / 变异假阳性 / 视觉误报×2） |
| 新建工具 | 5 个 |

**这张表要一直留着**。如果再来两轮还是"测试体系 bug 6 : 产品 bug 1"，
说明投入方向错了 —— 该把时间还给游戏本身。

## 十三、基线的粒度：不是「红不红」，是「谁该修」（v156.41 清账后立的规矩）

2026-11-02 清账：4 条「已知失败」逐条查下去 ——

| 结论 | 条数 |
|---|---|
| 真产品 bug（选州无效，出生点永远在别的州） | **1** |
| 判据用错了数据源（拿展示帧当结算账） | 1 |
| 测试环境脆弱（±8 格找不到低阶野地） | 1 |
| 断言过时（函数签名加了个参数） | 1 |

**4 条里 3 条是测试自己的问题**，却和那 1 条真 bug 挂在同一张表里，
同一个标签叫「已知失败」。看的人默认"这些难修、先放放" ——
于是**选州无效这个玩家能感知的 bug 陪跑了很久**。

规矩：

1. **进基线前先判类型**：
   - 改断言能解决的（签名/类名/文案变了）→ **当天改掉，不许进基线**（成本 2 分钟）；
   - 只有真要改产品、且一时改不完的，才进基线，并在 note 里写「谁该修 / 大概多久」。
2. **基线不是"红名单"，是"欠条"**。欠条要有还款日。tier_audit 的 Q2 按 since 催。
3. 看到 gate 输出「N 条基线可收缩」，意思是**那些已经好了、该从表里划掉** ——
   立刻 `--update-baseline`，别让废条目占着位置。

**当前状态：基线为空**（2026-11-02，smoke 4418 通过 / 0 失败）。
这是本项目的正常态：**门禁要求全绿**，不再有"合法的红"。

## 十四、层次与依赖：三层是**打包分组**，不是分层约束（2026-11-02 体检）

`js/modules.json` 的 `bundles`（core 53 / war 9 / ui 24）只决定**文件拼进哪个包**，
`build_bundle.py` 从不校验依赖方向。实测：**65 条反向调用边 / 177 个调用点**，
其中 **69% 是 compute** —— 计算函数被放在了上层。

```
prologue [core] → ui      31 处
battle   [war]  → story   24 处（全 compute）
state    [core] → battle  17 处
state    [core] → story   15 处（全 compute）
```

**最典型**：`js/story.js` 在 ui 包里，却提供 `prodMult` / `cityDefMult` / `troopPower` / `combatMod`
—— 决定全局数值的规则住在 UI 包。改一个天气系数，在依赖图上等于"改了 UI"。

### 台账（不是违规清单，是"从未立规"的证据）

```bash
node .workbuddy/tools/prof/layer_debt.js          # 现状
node .workbuddy/tools/prof/layer_debt.js --diff   # 新增/还清（有新增退出码 1）
node .workbuddy/tools/prof/layer_debt.js --update # 改了代码后重写
```
**重构前后各跑一次 `--diff`**：还清几条、新增几条，一眼看到。

### 测试的观察面错位（比依赖方向更严重）

4250 条 check 里：直接引用 **ui** 模块 **806** 条 / 直接引用 **core** **2** 条 /
不绑定任何文件 **3587** 条。**core 几乎没有被直接测过**，只被间接执行。
所以 core 算错了，现象出在 UI 上，定位链被拉长。

### ⛔ 「改这个文件要跑多少条」**无法事前估算**

| 口径 | ui-city | 问题 |
|---|---|---|
| 段级（`impact_of`） | 1694 | 271 条的段里 3 条碰到就全算给它，**虚高 19 倍** |
| 断言级（`assert_owner`） | 87 | 只覆盖 19% 的断言，**覆盖不足** |

根因：84% 的断言不断言具体文件，只断言"跑一遍之后的状态"。
**所以别估，改完跑 `smoke_fast`（222 秒）看哪里红。** 这也是"按需跳段"失败的真正原因。

## 十五、规则层在 core，界面在 ui（v156.43 起的一条真边界）

`js/rules.js`（core）放**只依赖 `DATA` 与 `state.world` 的纯计算**：
`currentSeason` / `currentWeather` / `prodMult` / `troopPower` / `combatMod`。

来历：这些原本住在 `js/story.js`（**ui 包**），被 battle 调 17 处、state 调 9 处、tactic 调 4 处
—— 改一个天气系数，在依赖图上等于"改了 UI"。
30 处调用点已改为直接走 `GAME.rules.*`；`story.js` 保留同名**转发**（未改的调用点照样工作）。

### 搬进 rules 的判据（只有一条）

> **只依赖 `DATA` 与 `state.world` 的纯计算。**

反例 —— 这些**不该**搬：
- `cityDefMult` / `bondBonus`：依赖 `STORY.activeBonds()`（另一个业务系统）→ 留在 story
- `init` / `skyLine` / 播报：事件与界面 → 留在 story
- `map3d.rebuild` 这类：依赖 THREE/WebGL → **永远不进 core**，否则渲染塞进数据中心

### 还剩多少

`layer_debt --diff` 看现状：**147 处 / 65 条边**（原 177）。剩下的按性质：
compute 92 / open-ui 22 / notify 18 / refresh 15。
**这些是欠条，不是待办** —— 什么时候改到那儿，什么时候还。**不立规则**（立了就要还完，否则门禁永远红）。
