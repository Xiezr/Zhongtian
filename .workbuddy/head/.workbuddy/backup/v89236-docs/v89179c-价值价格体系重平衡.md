## 二、三条分别怎么落的

### ① 快购误弹全类商品（真 bug）

- **病根**：`ui.js` 快购弹窗里的「买入」按钮只带 `data-cat`，**没带 `data-scope`**；
  买完后 `main.js` 用 `openQuickCat(cat, el.dataset.scope || null)` 重渲染 → **scope 丢失** →
  从"训练入口"进来的弹窗，买一次之后就把研究/建造/行军/交易**整类**端上来了。
- **修法**：给买入按钮补 `data-scope`，重渲染保留用途过滤。
- **断言**：smoke `⑧c⑦`（真调 `ui.openQuickCat('boost','train')` 抓渲染串 —— 按钮必须带
  `data-scope="train"`，且弹窗里只能出现**训练用途的在售**宝物）。

### ② 价值价格体系重平衡（三道闸）

**根因**（不是"混乱"，是有结构性漏洞）：
训练加速宝物原先全是「金币商城 + 可叠加 + 无总上限」——
`韩信点兵术(-50%) + 典兵残卷(-40%) + 虎符军令(-75%) + 十万甲兵(-90%)` 叠一条队列，
`elapsed` 直接顶满；而金币是全境单一池、**无限增长**（俸禄 + 产出 + 剧情倍率）→ **后期无限募兵成立**。
「花金买时间」同理：原最高档 100% 瞬完、且无上限。

| 闸 | 改法 | 落点 |
|---|---|---|
| **A 比例上限** | `DATA.BOOST_CAP = 0.30`：**宝物 + 花金合并**最多削 30% 时长（自然耗时至少 70%）。 | 唯一出口 `GAME.boostRoomOf(q)`（计 `q.boosted` 跳过量，**不与自然推进混淆**）→ `S.boostTrainQueue` / `S._boost` / `GAME.trainRush` 三处共用 |
| **B 获取难度** | 9 件 `pct ≥ 0.5` 加 `dropOnly`：**商城 / 快购不列** + `doShopping` 硬闸（与 `noShop` 同档）。 | `data.js` 物品表 + `ui.shopItems` + `ui.qbScopeItemsOf` + `main.js` |
| **B 配套 掉落** | `DATA.BOOST_DROP` + 唯一出口 `GAME.grantBoostDrop`（与 `SEED_DROP`/`ESSENCE_DROP` 同构）：采集归来（主 · mult=1）+ 出征缴获（次 · ×0.7）。**移出商城 ≠ 绝版**。 | `domain.js`（采集线）+ `battle.js`（缴获线） |
| **C 花金封顶** | `TRAIN_RUSH.steps` 由 25/50/100% 重设为 **10/20/30%**（删「立刻完成」档）；报价按**实际可削比例**折算（**报价 = 实收**，不虚报）。 | `data.js` + `GAME.trainRushCost` + `GAME.trainRush` |

## #4 行军加速（march）—— 调查结论：**本轮不改，请老板拍板** ⏸

**查到三件事（都有代码定位）：**

1. **道具路径无封顶**：`S._boost` 的 `target === 'march'` 直接调 `GAME.march.rushAll()`
   → **立即完成当前全部行军**，完全绕过 `BOOST_CAP`。
2. **UI 有一个免费的同一功能**：`ui.js:1327` / `ui.js:2949` 各有一个
   `data-action="march-rush"` 的「⚡ 急行军令（立即抵达）」按钮，`main.js:101` 处理时
   **不扣金、不消耗道具**，直接 `rushAll()`。→ **付费的急行军令 / 疾行令被免费按钮完全压死**。
3. **`rushAll` 还有第三个调用者是"离线结算"**（`state.js:1897`）：离线补算后把"早该抵达"的行军一次结清 ——
   那是**正确性**需求，不能顺手给它封顶。

**道具数据本身也不自洽**：
- 急行军令 `amount: 10` · desc「行军时间缩短为10秒」
- 疾行令 `amount: 30` · desc「行军缩短 1 小时」
- 但两者**行为完全相同**（全量瞬达）→ `amount` 对它们等于**死字段**，desc 与实际**不符**。

**为什么没动**：v89.104 的记录显示"急行军"按钮是老板当时要的（军务/出征页逐行「急行军」），
是否收费 / 是否封顶属**平衡决策**；而 `rushAll` 被离线结算共用，硬封顶会破坏正确性。故先给证据与选项。

| 选项 | 做法 | 代价 / 效果 |
|---|---|---|
| **A 封顶** | 道具与按钮统一走 `BOOST_CAP`（每条行军最多削 30%），desc 按新口径重写 | 行军时机重新有约束；但 v89.104 的"立即抵达"便利消失，需定义 `amount` 口径 |
| **B 收费**（我推荐） | 保留"立即抵达"，但免费按钮改为**消耗一枚急行军令**（无道具则引导去快购）；两条 march 道具 desc 改为"立即完成当前全部行军" | 保住 v89.104 的便利入口，同时让道具**真正有价** —— 正对老板"价值价格体系混乱"的症结 |
| **C 维持** | 只把 desc 改成与行为一致，接受行军时机无约束 | 最小改动；但付费道具仍是免费按钮的影子，属于"鬼商品" |

## 7.1 B 方案：行军即刻抵达必须消耗道具

**改前三处问题**（均已在上一节取证）：
1. `ui.js:1327` / `ui.js:2949` 各有一个**免费**「⚡急行军令（立即抵达）」按钮，`main.js` 处理时**不扣金不耗道具** → 付费道具被完全压死；
2. `main.js` 里"带 `data-id` → 只催这一支"的分支**没有任何模板发射** → **死分支**（等于"逐行急行军"从未存在）；
3. 急行军令 `amount:10` / 疾行令 `amount:30` 是**死字段**，desc（"缩短为10秒"/"缩短1小时"）与实际行为不符。

**改后分工**：

| 按钮 | 消耗 | 效果 | 位置 |
|---|---|---|---|
| ⚡ 急行军（令 N） | 急行军令 ×1（15 金） | **单支**即刻抵达 | 行军表**逐行**（三处表格统一，`ui.marchOpsCell`） |
| ⚡ 疾行令 · 全部即刻抵达（持有 N） | 疾行令 ×1（40 金） | **全部**即刻抵达 | 面板底部（`ui.marchRushAllBtn`） |

- **唯一出口**：`GAME.march.rushApply(marchId)`（纯效果，不碰道具）+ `GAME.march.rushByItem(itemId, marchId)`（作用域校验 → 道具校验 → 调效果出口 → 扣 1）。
- `rushAll` 保留为 `rushApply(null)`，**仅供离线结算**（`state.js:1897`）—— 那是正确性需求，**不消耗道具**。
- 背包路径：疾行令 → 立即完成全部（扣减沿 `useItem` 的统一出口）；**急行军令 → 明确指路**（"用于单支，请到行军队列点该行"），不做静默的"顺手全催"。
- 缺道具时按钮**仍可点** → 提示 + **就地开快购**（买成后回到行军队列）—— 不留"点了没反应"。
- 数据：两支道具加 `marchScope: 'one' | 'all'` · 删死字段 `amount` · desc 改正。
- 顺带**复活了死分支**，并让"免费全量"这条路彻底消失。

## 7.2 周期配额（B 闸的另一半）

`DATA.BOOST_DROP.quota = { perRealDay: 6 }` + 唯一出口 `GAME.boostDropLeft()`：
高阶加速宝物**按现实日**最多掉 6 件（采集 + 战役合计），用满即停、次日自动回满。

**为什么必须限量**（实测口径，见 `_v89179c_drop.txt`）：
采集是"每队满 1 游戏小时可收获 · 同时最多 3 队"（`DATA.GATHER.minHours` / `maxActive`）
→ 一天最多 72 次收获；Lv10 单次期望 0.403 件 → **无配额时约 29 件/游戏日**；
600× 下 1 现实日 ≈ 600 游戏日 → **现实里刷几分钟就能囤上千件**。

**为什么用现实日**：与 `GAME.autoMarchRollDay`（自动出征每日上限）**同一把尺子** ——
现实日节流才是防刷；游戏日在 600× 下形同虚设。

## 8.1 本轮新抓出并修复

### ① 建造退款按**原价**算、付款按**折扣价** → 资源泵漏洞（真 bug，可无限刷资源）

- **病根**：`GAME.cancelRefundOf` 从**数据表反查原价**，退 `原价 × 80% × 剩余时间比例`；
  而城内建造是**按折扣价付款**的（`applyBuildCostDiscount`）。
  于是开「匠神尺（建造成本 −50%）」后 **建造 → 立即取消**，付出 50%、拿回 80% → **净赚 30% 原价资源**；
  刚开工时 `remainRatio ≈ 1`，可反复刷（只受道具 24h 时长与金价限制）。
- **修法**：队列在付款时记录 `paidCost`（`GAME.resOnlyOf(cost)`，只含资源键），
  `cancelRefundOf` **优先读 `paidCost`**；旧档队列没这个字段 → 回落原价反查（行为同旧）。
- **断言**：smoke `⑧c⑪`（实付 = 折扣价 · 退款 ≤ 实付 · 旧档回退原价）。

### ② 城外建造**不吃**建造费折扣 → 描述与实现不符（同属老板②）

- **病根**：`if (buffActive('buildCost')) cost = applyBuildCostDiscount(cost)` 只在
  城内两处 + 城墙面板各写一遍；**城外（`buildExt` / `upgradeExt`）与城外面板全漏**。
  可三件道具的 desc（营造方略 / 将作大匠令 / 匠神尺）都写"建造成本 −X%"，**没有"仅城内"**。
- **修法**：新增**唯一出口** `GAME.buildCostDiscountOf(cost)`，城内/城外 × 后端/界面四处全走它；
  城外面板三处显示（升级价 / 可负担判定 / 选择卡 hover）同步改读折扣价（不留"hover 原价、面板折扣价"两本账）。
- **口径统一**：**成本打折 · 工期不动** —— `applyBuildCostDiscount` 会把 `cost.time` 一起乘折扣，
  而"成本"是资源不是工期；旧写法还造成城内自相矛盾（新建读原始 `lc.time`、升级却读了打折后的 `cost.time`）。
- **断言**：smoke `⑧c⑩`（成本打折 · 工期不动 · 无 buff 原样）+ `⑧c⑪`（城外真调 `buildExt` 实付 = 折扣价）。

### ③ 体力/精力回复速率公式两处重复（观察项① 结项）

- **修法**：收敛为唯一出口 `GAME.recoverRatePerRealSec()`（在线 `tickOnce` 与离线 `simulateBulk` 各一份 → 合一）。
- **判定（不改数值）**：v89.131「按现实时间 24h 回满」是**老板明示**；
  `DATA.GEN_COST` 注释里明写"与倍速解耦"是设计目标；界面（`ui.js:8810` / `9031`）**已向玩家写明"与倍速无关"**。
  ⇒ 「600× 下行动被体力卡住」是该设计的**后果**，不是 bug —— **不擅自反转**。
- **留一行开关**：`DATA.GEN_COST.recoverSpeedScale`（默认 `'off'` 严格保持原口径；
  `'sqrt'` = 回速 × √倍率，600× 时约 1 现实小时回满而非 24）。改时须同步改界面文案与 §112② 断言（已在注释写明）。
- **断言**：smoke `⑧c⑫`（默认口径不变 · 1× 完全相同 · sqrt 分支可用）。
