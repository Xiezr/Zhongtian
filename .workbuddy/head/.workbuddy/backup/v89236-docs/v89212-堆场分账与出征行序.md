## ① 城外堆场按资源分账（老板 1）

### 病根（一句话）

`extStoreCapOf` 把 **Σ（所有地块等级）** 摊给四种资源**共用** —— 农田多不多、林场多不多，
四类上限一模一样（改前基线实证：4田1木 与 1田4木 两城，粮/木/石/铁上限全等 366.7万）。

### 改法（唯一出口组 · 表）

| 出口 | 改前 | 改后 |
|---|---|---|
| `GAME.extStoreCapByResOf(city)` | （无） | **新增底账**：{ grain, wood, stone, iron } —— 农田只堆粮 / 林场只堆木 / 石场只堆石 / 矿场只堆铁；逐类在"该类等级和"上取整一次（合计 = Σ分账，账目自洽） |
| `GAME.extStoreCapOf(city[, key])` | 单参 = Σ全部 | 无 key = 四类合计；**带 key = 该类**（按 `EXT_BUILDINGS[type].res` 归类） |
| `GAME.storePartsOf(city)` | { base, ext, total, lv } | 增 **`extByRes` / `capByRes`**（`capByRes[k] = base + extByRes[k]`）；ext/total 保留（合计口径） |
| `GAME.storeCapOf(city[, key])` | 单参 = total | **带 key = 该资源上限**（业务判定）；不带 key = 合计（展示/兼容） |

**五处业务消费点全按资源**：

| 消费点 | 改后形态 |
|---|---|
| `tickOnce`（在线逐秒） | 每城 `storePartsOf(ct).capByRes` 一次 → 循环内按资源查表 |
| 离线 bulk / `simulateOfflineOverflow` | 同款（三处循环统一，每城算一次 · 不在循环里重复算） |
| `overflowRotOf`（逾溢折损） | 逐资源 `cap = caps[k]`（超**各自**上限才折损） |
| `addResCapped`（奖励入账） | `storeCapOf(ct, key)` |
| `transportPlanOf`（运输余量） | `storeCapOf(to, key)` |
| `systems._openChest`（开箱截断） | 逐资源 `storeCapOf(currentCity(), k)` |

**UI 同步 5 处**：资源栏悬停（本资源上限 +「· 城外堆场（本类地块）：+X」）· 仓库面板（四行各显各的
上限，行悬停给「仓库 X + 城外堆场 Y」分解；空仓库提示按资源列账）· 建造面板（本城上限四资源）·
城外面板（「另加<归属资源>上限」如"另加石料上限"）· 选建悬停（"每级另加<资源>上限"）。

### 实测证据（探针 probe_v89212a_ext.js · 同一支改前跑红 / 改后全绿）

### 数值影响（如实）

- 单块口径不变（等级 × BASE_STORE ÷ 6 = 同级仓库容量的 1/6）；
- **逐类上限对非主导资源会低于改前**（改前四类共享全部堆场）：首城木/石/铁 366.7万 → 233.3万，
  粮 366.7万 → 266.7万。这是"露天堆场与产地对应"的直接推论（农田旁堆粮、林场旁堆木）；
- 全城堆场**总量**（四类相加）不变（首城 166.6666万，取整差 1 见下）；
- ⛔ 取整口径：**逐类取整再相加**（账目自洽：合计 = Σ分账）——与旧"总和取整一次"最多差 ≤3
  （首城 1666666 vs 旧 1666667）。如需恢复旧总量尺度，调 `DATA.EXT_STORE_DIV` 一个数即可（现 6）。

2. 仓库面板的"四行各显各的"布局观感（实机图 v89212-store.png）。

## 诚实缺口

1. **取整差异**：合计 = Σ分账（逐类取整）与旧"总和取整"差 ≤3（账目自洽优先）——
   已写进 smoke §122② 期望值（4999999 = 3×333333 + 4000000）；
2. 仓库面板"四行上限 + 悬停分解"是新增展示面，承载在现有 `.store-row` 行内（无滚动条 ·
   modals 审计随门禁复核）；
3. NPC 库藏基准（`resByTier`）仍按**合计口径**交叉校验（`storeCapOf(fake)` 无 key）——
   数值未变（§v89.81 断言全绿）；玩家侧"按资源上限"是更细的一层，二者不冲突。
