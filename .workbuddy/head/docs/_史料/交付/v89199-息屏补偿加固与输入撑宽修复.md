## 一、需求 ②「逐个输入数字后整页逐渐放大」——病根与修复

### 1.1 病根（真机复现 + 元素级定位）

**不是输入框的问题、不是重绘的问题 —— 是「待补清单」把整页撑宽了。**

自动征兵面板下部「各城栏位与缺口」区的「待补」清单**逐项累积**（每个参与兵种一项：
"民夫 差 9,999、义兵 差 9,999、…"），而它所在的 `.res-line .val` 是**全站通用样式
`white-space: nowrap`**（资源行数值不换行的设计）→ 该行的 min-content 撑到 **2076px**；
`.auto-grid` 是 `grid-template-columns: 1fr 2fr`（**1fr = minmax(auto, 1fr)，会被 min-content 撑开** ——
v89.132 记录过的老坑）→ 右列被撑 → `ui-page` → `#view-container` **整页被撑宽**：

```
实机实测（1600×1000 视口 · k=1.1111 · 初始 vcSW=1408）：
  第 1~12 框    vcSW=1408     （待补不足 6 项，未到临界）
  第 16 框      vcSW=1537     ← 开始被撑（+129）
  第 20 框      vcSW=1770（+233）
  第 24 框      vcSW=2004（+234）
  第 32 框      vcSW=2383（溢出元素 37 个）
  终态：ui-page=2383 / auto-grid=2355 / auto-pane=2124 / 最宽 val=2076
```

「逐个输入数字 → 每次激活一个兵种 → 待补 +1 项 → 页面宽一点」——
老板看到的"整个页面逐渐放大"就是这个。

### 1.2 改法（三级防御 · 真机注入验证后定稿）

| # | 落点 | 改前 → 改后 | 为什么 |
|---|---|---|---|
| ① 核心 | `ui.js` autoTrainHTML 两行 `.res-line`（各城缺口行 + 触发记录行） | `class="res-line"` → `class="res-line wrap-ok"` + 新 CSS `.res-line.wrap-ok`（`flex-wrap:wrap` + `.val` 的 `display:inline; white-space:normal; overflow-wrap:anywhere`） | **换行许可**：val 的 min-content 从 2076 → 878（可折行） |
| ② 配合 | `index.html` `.auto-grid` | `1fr 2fr` → `minmax(0, 1fr) minmax(0, 2fr)`；`.auto-pane` 加 `min-width: 0` | 锁住轨道比例（**单独用会反效果** —— 见 1.3） |
| ③ 兜底 | `index.html` `.view-box` | `overflow-y: auto` → `overflow-y: auto; overflow-x: auto` | 任何来源的横向溢出不再撑破祖先（视图页允许滚动 · 既有口径），内部滚动兜底 |

正常宽度下「待补」**不折行** → 视觉零变化；只有内容真超宽才折行。

### 1.3 修复配方是"成对"的（真机注入对照，缺一不可）

```
[撑大后]          vcSW=2383  （最宽 val=2076）
[+grid minmax(0)] vcSW=2589  ⚠️ 单独加 minmax 反而更糟（内容溢出轨道、往外顶）
[+val 可换行]     vcSW=1408  ✅ 完全恢复
[+pane minw:0]    vcSW=1408  （保持）
```

### 1.4 实测证据（修复后）

```
修复后重跑全量 32 框输入：
  初始 → 第 32 框 → 终态：vcSW 恒 = 1408 = vcCW，溢出元素 = 0（全程 10 个采样点）
实机验收：
  ①a 页面不被撑宽（1408 → 1408）          ✓
  ①b 无横向溢出（SW===CW · 溢出元素 0）    ✓
  ①c 输入生效 + 「待补」15 项俱在          ✓
  ①d 长文本折行渲染（val 976×65，3 行档）  ✓
```

## 二、需求 ①「息屏过夜补偿不生效」——加固交付

### 2.1 取证结论（探针两轮）

**离线补算链本身完好（真机拨钟实测）**：

```
复杂状态（多队列 + 行军在途 + 自动征兵开启）下拨钟 8h：
  gap=28800 → mode=catchup（无异常）
  world.elapsed 5400 → 3,461,784（Δ=3,456,384 ≈ 8h×120 精确）
  募兵队列被补算完成（队列清空、兵入营）——这正是老板要的"过夜回来看到完成"
```

**当前无法在实验室复现"息屏不生效"的确定性场景**（CDP frozen 对前台页不生效；
系统睡眠无法模拟）。据此收窄出两个**真实存在的风险面**：

| # | 风险 | 依据 |
|---|---|---|
| A | **唤醒时机**：setInterval 在系统睡眠 / 标签冻结期间停摆，恢复后要等下一拍才发现缺口（极端情况下 timer 恢复慢半拍） | 主循环此前只有 setInterval 一条通道 |
| B | **旧会话代码**：页面"长开不刷新"时一直跑**打开那一刻**的 JS —— 更新文件后旧页面不换新代码。**老板"真离线可以、息屏不行"的分野恰好吻合**：关页面重开会加载新代码（走读档补算=可以）；不关页面测的是**旧会话**（可能连 v89.193 的时钟锚都不在场） | file:// 无自动更新机制 |

### 2.2 加固（针对 A + B）

**A. 时间推进的唯一出口 + 双通道（state.js / main.js）**

```
GAME.loopPulse(checkVisible)          ← 唯一出口（记账 + 决策 + 补算）
  ├─ setInterval 每秒调用（原路径）
  ├─ document visibilitychange → visible 时**立即**调用    ← 新增
  └─ window focus             → 获焦时**立即**调用          ← 新增
幂等：谁先消费 gap，后到者见 ~0 即 skip —— 通道叠加不重复推进。
```

- `loopGapCatchup` 降为薄包装（同源转发，老测试/工具零改动）；
- **异常防护（新增）**：补算抛异常不再让整拍 tick 崩掉 —— 留痕 `console.warn`
  并把锚点回退到 60 秒前（下拍自动重试这一小段；避免"异常一次吃掉 8 小时"的整段丢失）；
- 非游戏界面（hidden）只记账不补算（保持 v89.193 口径）。

**B. 运行时版本标识（唯一来源）**

- `GAME.VERSION = 'v89.199'`（main.js · 每轮迭代更新）；
- 设置页末卡新增「🧩 运行版本」行 + 指引「若与最新交付不一致：按 **Ctrl + F5** 强制刷新」。

### 2.3 实测证据

```
②a 已进入"刚拍过"窗口（距上次主循环拍 <80ms）——此后 ~900ms 内无 interval 拍
②b focus 事件后 260ms 内补算已发生（world Δ=3,456,000，需 ≥3,110,400）  ✓ 独立通道实证
②c 补算提示 toast 在册（含"时间跳变"）                                   ✓
③  GAME.VERSION=v89.199 + 设置页含「运行版本」与 Ctrl+F5 指引            ✓
```

**②b 的判据设计**：刻意等到"距上一次主循环拍 <80ms"再拨钟——此后 900ms 内没有
interval 拍，260ms 内补算发生**只可能来自唤醒通道**（确定性，非概率）。

## 四、诚实缺口

1. **「息屏不生效」的最终定谳需要老板端验证**：请**先按 Ctrl+F5 强制刷新**（设置页
   确认版本 = v89.199）**再过夜测试**。若刷新后仍复现"不生效"，请告知浏览器
   （Chrome/Edge）、是否装节能扩展、电脑是否真睡眠——这几项决定下一步方向。
   （"旧会话代码"是当前最高嫌疑：不刷新的页面永远跑旧代码，这一点在任何时候都成立。）
2. 触发记录行（logRows）同样加了 wrap-ok，但新局无记录时该行不渲染——
   实机只量到城市缺口行 1 个；记录行折行行为未专项量测（结构相同，风险极低）。
3. 同类观察点（本轮未改）：v89.165 的"遣散记录"行（`items.join('、')`）与烽火页
   "建议"长文案行同为 `nowrap` 累积/长文本形态——当前宿主宽度足够；若未来变窄会先
   被 `.view-box` 横向滚动兜底，不会撑破整页。
4. CDP `setWebLifecycleState('frozen')` 对前台页面不生效（浏览器正确行为），
   "真实系统睡眠唤醒"的 timer 恢复行为无法在实验室复现——**拨钟法**是等价验证的最强手段。
