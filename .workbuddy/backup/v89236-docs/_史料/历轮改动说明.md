## 一、六项改动

| # | 项 | 原版 | 改前（我们） | **改后** | 参数位置 |
|---|---|---|---|---|---|
| 1 | 战场距离 | 双方最远射程 **+199** | 场地常数 2000/3000/4000 | **双方最远射程 + 199** | `tactic.battlefieldOf()` / `T.FIELD_MARGIN` |
| 2 | 反击 | 双方都在射程内时，守方按**被打后数量**反击 | ❌ 无 | **已补**（无递归） | `tactic.js` 的 `counterStrike()` |
| 3 | 半程/贴身衰减 | 半程内全伤害 / 半程外半伤害 / 贴身 1/4 | ❌ 无（只有"首轮 ×1.3"） | **已补**（仅对远程） | `T.rangeDecay()` / `DECAY_FAR` `DECAY_CLOSE` |
| 4 | 相克 | 两套说法（A 官方互克 / B 玩家实测） | 单向 ×1.5 | **B 套：分方向攻/防两向因子** | `DATA.COUNTER_ATK` / `COUNTER_DEF` |
| 5 | 回合上限 | 30（野战） | tactic 40 / battle 60 | **30**（两引擎同口径） | `T.MAX_ROUNDS` / battle 的 `maxRounds` |
| 6 | 速度→位移 | 1:1（速度即每回合步数） | ×2.4（我们自定） | **1:1** | `T.MARCH_UNIT = 1` |

### 1. 战场距离 = 最远射程 + 199

```
战场距离 = max(攻方最远有效射程, 守方最远有效射程[, 城头火力射程]) + 199
有效射程 = 兵种射程 × (1 + 抛射科技) × 天气修正
```

**近战射程也参与比较**（原版自洽验证：无远程无城防时战场距离 270，而近战里最远的是铁骑 70 →
`70 + 200 = 270` ✓）。保底 `T.FIELD_MIN = 200`（双方都是义兵时是 219）。

⚠️ **顺手解掉一个循环依赖**：城头火力射程原本是 `min(纵深, 300 + 城防×35)`，
而纵深又要用"最远射程"来算 —— 直接套会变成"纵深决定火力、火力又决定纵深"。
所以拆出 `wallFireRangeRaw()`（原始值，参与纵深计算）与 `wallFireRange()`（钳制到纵深内，实战用）。

**为什么这是唯一的"结构性"改动**：抛射科技从此不只加射程，它同时**把开战间距推远** →
远程方拿到先手。实测：同样 5000 义兵对 5000 义兵，纯近战纵深 **219**、带弓 **1159**、
带投石 **1799**（开局间距 20 → 1399）。

### 2. 反击

原版原文：「如果双方都在射程内，则攻击方的每次进攻都将遭到防御方的反击。
**其反击人数按照被攻击后的数量计算**。」三条要点逐条落地：

- 触发条件 **双方都在射程内**（`gap <= 被攻击者的有效射程`）—— 隔空打够不着的人，不会被反击；
- 反击用的是 **被打完之后剩下的兵**（`fireOnce` 已扣过 `def0.count`）—— 实测同一场里
  守方"主动攻击杀伤 2250 / 挨打后反击杀伤 750"，反击明显是**残部火力**；
- **无递归**（反击不再触发反击）—— 否则两支远程对射会无限循环。

顺带把"开火"抽成 `fireOnce()` 供主动攻击与反击**共用**：两处若各写一份伤害算法，
"反击伤害偏低"会变成一个查不出来的暗偏差。

### 3. 半程衰减 + 贴身惩罚

```
间距 ≤ 120 丈（贴身）      → ×0.25
间距 ≤ 有效射程 / 2        → ×1.00（全伤害）
否则                       → ×0.50（半伤害）
```

⚠️ **只对远程生效**（射程 ≥ 500 的弓/弩/投）：近战本来就是贴脸互殴，
给它算"贴身惩罚"等于把所有近战伤害一律除以 4，回合数会翻几倍。

### 4. 相克：B 套（分方向两向因子）

`COUNTER_ATK[我][你]` = 我打你时**我的兵攻** ×N ｜ `COUNTER_DEF[我][你]` = 我挨你打时**我的兵防** ×N

| 方向 | 关系 | 因子 |
|---|---|---|
| 攻击向 | 长枪打骑兵（含突骑/虎豹/西凉铁骑） | ×2 |
| 攻击向 | 床弩打器械（冲车/辎重/投石/床弩） | ×3 |
| 防御向 | 刀盾防远程 | ×3 |
| 防御向 | 轻骑防远程 | ×4 |
| 防御向 | 铁骑防远程 | ×2 |
| 防御向 | 冲车防弓（**不防弩、不防投**） | ×5 |

**B 套明确否掉 A 套的两条**：「盾打枪和骑打弓都没有任何加成」—— 在新结构里这两条
不是"被削弱"，而是**压根不存在**（表里就没有）。旧的那张单向互克表 `DATA.COUNTER`
与 `COUNTER_MULT = 1.5` **已删**，不留第二出口。

`dice`（可切换的回退引擎）同步改了：攻击向读同一张表，防御向按"守方对该兵种的最高因子"折算成除法。

### 5 / 6. 回合上限 30 + 推进 1:1

- `T.MAX_ROUNDS` 40 → **30**，`battle.js` 的 `maxRounds` 60 → **30**（两引擎同口径）。
  实测：20 组对等战**没有一组**撞到 30 回合上限，说明 30 够用。
- `T.MARCH_UNIT` 2.4 → **1**（速度即每回合丈数）。原版战报实录里步数 ≈ 满科技速度本身
  （轻骑前进 1500、铁骑 900、长枪 600），1:1 才逐项对得上。
  `stepsToWall(spd, range, kind)` 的签名改成 **`stepsToWall(spd, range, D)`** ——
  纵深已经是配兵的函数，"按场地种类查表"不成立了。

## 二、顺带修正：我上一轮报告里的一处误判

**「同速时谁先行动」** —— 检索报告第十一章把它标成"✅ 同"，那是**误判**：
我只核了"按速度排序"，没核"同速谁先"。实际代码是 `x.side === 'atk' ? -1 : 1`（**攻方先**），
而原版多源一致写的是「速度相同时，**防守方先行动**」—— 正好相反。

已改为守方先。这条在"同兵种对拼"里是决定性的：实测修正前是
"攻方主动杀伤 750 / 反击 750"（看不出残部效应），修正后是
"主动 2250 / 反击 750"（守方先手，一次齐射就打出优势）。

## 三、实测（新口径）

### 相克两向在实战里的效果（同兵力 1000 对 1000）

| 对战 | 结果 | 说明 |
|---|---|---|
| 弓 → 长枪 | 弓胜，长枪全灭 | 长枪无防御向 |
| 弓 → 刀盾 | **刀盾胜**，弓全灭 | 刀盾防远程 ×3 |
| 弓 → 轻骑 | **轻骑胜**，弓全灭（轻骑只损 16.6%） | 轻骑防远程 ×4 |
| 弓 → 冲车 | **冲车胜**，弓全灭（冲车只损 2.1%） | 冲车防弓 ×5 |
| 投石 → 冲车 | **投石胜**，冲车全灭 | 冲车**不防投石**（原版明确） |
| 床弩 → 冲车 | **床弩胜** | 床弩打器械 ×3 |
| 刀盾 → 长枪 | 长枪胜 | B 套：盾打枪**无加成** |

### 带不带远程（同总兵力 2000 对 2000，对手是纯长枪）

| 编成 | 纵深 | 回合 | 结果 | 攻损 |
|---|---|---|---|---|
| 纯长枪 2000 | 239 | 2 | 攻胜 | 50.0% |
| 弓 500 + 长枪 1500 | 1159 | 5 | **守胜** | 100% |
| 弓 1000 + 长枪 1000 | 1159 | 4 | 攻胜 | 51.3% |
| 弓 1500 + 长枪 500 | 1159 | 3 | 攻胜 | **37.1%** |
| 纯弓 2000 | 1159 | 3 | 攻胜 | **0.0%** |

→ 远程的收益随**占比**上升；而只要带上远程，纵深就从 239 抬到 1159（近战要多走 4~5 回合）。

- 战场距离 = 最远射程 + 199（**按同一套倍率反算**，不写死数字 —— 射程受科技与天气影响）

- 衰减三档 + 只对远程生效
- 相克查询**收兵种 id**（签名不一致会让整套防御向静默失效 —— 我踩过）

- 旧 `DATA.COUNTER` / `COUNTER_MULT` 已删（防第二出口回归）

- 回合上限 30（两引擎同口径）+ 20 组对等战不撞上限

## 一、战斗：把 v57 文档里"仍与原文有差距"的前两项做掉

### 1. 抛射科技 4%/级 → **5%/级**（对齐原版）

`DATA.TECH` 的 `paoshe.per` 0.04 → 0.05，科技上限本来就是 10 级（`domain.js` 的升级守卫
`(s.techs[t.id] || 0) < 10`），所以满级倍率从 ×1.4 变成 **×1.5**。

**为什么这项不是"微调"**：v57 把"战场距离 = 最远射程 + 199"落地后，抛射不再只加射程 ——
它同时**把开战间距推远**。改完实测（无天气修正时）：

| 兵种 | 基础射程 | 满抛射射程 | **战场距离** | 原版公开实测值 |
|---|---|---|---|---|
| 弓箭手 | 1200 | 1800 | **1999** | 1999 ✅ |
| 床弩 | 1400 | 2100 | **2299** | 2299 ✅ |
| 投石车 | 1600 | 2400 | **2599** | 2599 ✅ |

**三项逐项精确对上原版公开值** —— 这也反向验证了 v57 的战场距离公式是对的。

### 2. 城防做成**独立火力源**

原版城墙自带箭塔 / 擂石 / 滚木（箭塔射程 2500），**不依赖守军带不带远程兵**。
我们此前只有"城防值放大守方远程的射程"，于是**守军全近战时城头完全不还手** ——
"守城"少了一半含义。

现在：

```
城头火力攻击值 = 城防值 × T.WALL_FIRE_PER_DEF(120)
```

- 每回合开火一次（`wallVolley`），**不进兵力统计**（`atkStartBy` / `loss` / `remain` 都不含它），
  工事不会"被打死"；攻城器械只能**压制**它（`CRAFT_FIRE_CUT` 仍生效）。
- 防御向按**远程**判定（`counterDefOf(tg.id, 'gongjian')`）——
  刀盾抗箭 ×3、轻骑抗箭 ×4、冲车防弓 ×5 都对工事生效（它们本来就是防箭的）。
- 实测（投石 5000 攻 城防 300 的城）：

| 城头火力 | 结果 | 攻损 | 城头累计杀伤 |
|---|---|---|---|
| 关掉 | 16 回合攻胜 | 645 | 0 |
| **120（现行）** | 16 回合攻胜 | **1413** | **768** |
| 40 | 16 回合攻胜 | 901 | 256 |

城防值越高攻损越大（0 → 0%、100 → 327、170 → 614、300 → 1413），**削弱但不压倒**。

#### ⚠️ 顺带修掉一个我在 v57 埋下的 bug

城头射程原公式是 `300 + defVal × 35`，**没有上限** —— 城防 300（城墙 Lv12）时就是 **10800**。
v57 把它并入"最远射程"比较后，**战场纵深被撑到 10999**，于是投石（射程 1600、速度 100）
要走 94 回合才够得着 → **30 回合上限内一箭不发**（实测：攻城方杀伤 0、守损 0，30~40 回合白打）。

修法：按原版口径给死上限 `WALL_FIRE_RANGE_MAX = 2600`（对齐原版箭塔 2500），
公式改为 `min(2600, 1200 + defVal × 5)`。

| 陷阱 | 0 | 0 | 0 | 2000 | 城墙 1 | 粮50 木500 石100 铁50 |
| 拒马 | 1000 | 0 | 180 | 800 | 城墙 2 | 粮100 木1200 铁150 |
| **箭塔** | **2000** | **300** | **360** | **1250** | 城墙 3 + 抛射 3 | 粮200 木2000 石1000 铁500 |
| 滚木 | 0 | 500 | 0 | 500 | 城墙 5 + 制造 4 | 粮300 木6000 |
| 擂石 | 0 | 800 | 0 | 250 | 城墙 7 + 制造 6 | 粮600 石8000 |

**只做箭塔**：五种里只有它是**持续火力**，其余四种是一次性消耗品（陷阱/滚木/擂石）
或纯障碍（拒马）。我们没有工事建造流程 —— 写进来而无消费点就是死数据（项目铁律）。

### 射程公式（照搬原版的**加法**口径）

```
箭塔射程 = 基础射程 × (1 + 抛射 5%/级) + 基础射程 × (城墙等级 × 3%) + 100（墙位移）
```

原版公开实测值：**十抛射十墙 → 1250 + 625 + 375 + 100 = 2350**，我们算出 **2350** ✅

> ⚠️ 是**加法**不是乘法：`1250×1.5×1.3 = 2437 ≠ 2350`。
> 检索报告 §5.1 那张表的算式写作"×+30%"有歧义，只有结论数字（2250 + 100）自洽 —— 按加法实现。
> `WALL_FIRE_RANGE_MAX = 3200` 只是防爆护栏（正常玩法上限：满抛射 + 都城城墙 24 级 = 2880）。

各城墙等级实测：

| 城墙等级 | 0 | 3 | 5 | 10 | 12（自建满） | 24（都城满） |
|---|---|---|---|---|---|---|
| 射程（抛射 0） | 1350 | 1463 | 1538 | 1725 | 1800 | 2250 |
| 射程（抛射满） | 1975 | 2088 | 2163 | **2350** | 2425 | 2875 |

### 三件机制（都照搬原版）

1. **箭塔是独立火力源**：座数 × 300（原版攻击）× 城头密集度修正，**每回合齐射一次**。
   射程参与"最远射程"比较 → **它自己就能撑起战场距离**
   （原版："箭塔射程 2500，我在 2600 还被打到"；我们实测：守军全近战时战场距离 249 → 1849）。
2. **双倍攻击区**：距离 ≤ 射程/2 + 100 时伤害 ×2
   （原版实测："箭塔 2350，双倍攻击区【0, 2250/2+100 = 1225】"）。
3. **箭塔可被摧毁**：耐久池 = 座数 × 2000 生命，把目标指定为箭塔即开始拆，
   火力随剩余座数线性衰减（原版战报：`[守]箭塔6138-2390=3748`）。

### ⚠️ 两个"我们特有"的系数（不是原版数据，必须说明）

| 常量 | 值 | 为什么必须有 |
|---|---|---|
| `perDef` | 0.5 | 原版由玩家**自己建造**工事，我们没有建造流程 → 把 `cityDefense()` 的城防值折成箭塔座数（每 2 点城防 = 1 座） |
| `tough` | 1200 | 原版伤害量纲比本作大两个数量级（原版单次杀伤百万级，本作几百）→ 直接套 2000 生命会**一回合拆光全城**。它只影响"拆箭塔要几回合"，不影响箭塔火力 |

`tough` 标定过程：投石 4000 打城防 200（100 座）——`tough=200` 时一回合拆 58 座（2 回合完事）；
改 1200 后约 9~10 座/回合 → **11~15 回合拆完**（与原版"十几回合清完城防"同量级）。

### 实测

| 场景 | 攻损 | 城头杀伤 | 箭塔 |
|---|---|---|---|
| 城防 0 | 0 | 0 | 0 座 |
| 城防 40（投石 4000 攻） | 123 | 24 | 20 座 |
| 城防 90 | 163 | 64 | 45 座 |
| 城防 150 | 207 | 108 | 75 座 |

**城防越高攻损单调越大** ✓

**双倍区只在"冲脸"时生效**：冲车（近战射程 50）冲上去 → 13/30 回合在双倍区；
投石/床弩（远程）停在射程边界 → 0 回合。
> 原因：我们的"前进"是**推进到刚好能开火就停**（v29 起的行为，对自动战斗友好），
> 所以远程不会自己撞进双倍区 —— 原版玩家要"主动后退到【1226,1799】处和箭塔对射"来**避开**它。
> 我们这层"贴脸更危险"的梯度同样存在，只是触发者换成了近战。

## 二、阵位与指挥指令（照搬检索报告 §九）

照搬原版（2024 新战术指挥系统）：

- 每个兵种两个变量：**动作**（前进 / 防御 / 后退）+ **目标**（敌方某一兵种）
- **动作决定初始站位**：前进 = **100**（第一排）/ 防御 = **50**（第二排）/ 后退 = **0**（第三排）
- 攻城时城墙在位置 100，"前排在城墙前"
- **指定目标在射程内 → 优先打它**；否则打射程内任意目标
- 原版把这件事设在「校场 → 出征 → 出征战术」

### 一处**两源冲突**，我做了裁决（需要老板确认）

| 来源 | 对"防御"的说法 |
|---|---|
| 检索报告 §九（2024 新版） | 本回合**不攻击** + 受到伤害**减半** |
| 老版战报（大量实证） | 原地不动，但**照常开火**（"TS 和 CN 防御不前进"明显还在输出） |

**裁决：取老版战报口径 —— 原地不动 + 受伤减半 + 照常开火。**
理由：若"不攻击"，守方默认防御会变成**完全不还手** —— 而原版攻城战里守方常态就是
"城墙原地防御"，与"守城方有先手优势""守军会反击"等其余全部资料矛盾。

### ⚠️ 一处按实测"补正"原版

**守方默认动作必须按场地分**：攻城 → 防御（照搬"城墙原地防御"）；**野地 → 前进**。

这不是我想当然：第一版做成"守方一律防御"后实测发现 ——
射程 50 的近战守军会在射程 1200 的弓兵面前**原地不动被白打整个 30 回合**
（同兵种 3000 对 3000：守方全灭、攻方零损失）。原版的"原地防御"是**守城**行为（有城墙可依），
不该推广到没有工事的野地。

### 实测

| 项 | 结果 |
|---|---|
| 初始站位 | 前进 100 / 防御 50 / 后退 0 ✓ |
| 首回合间距 | 前进最小、防御居中、后退最大；后退第 2 回合继续拉大 ✓ |
| **防御减伤** | 首回合守损 **11,138 → 5,569（精确 50%）** ✓ |
| **后退躲箭塔** | 弓兵后退：攻损 **0**（全程在箭塔射程外）；前进攻损 **512** ✓ |
| **目标偏好** | 指定打刀盾 → 首轮命中序列 `[刀盾, 长枪]`；自动 → `[长枪, 刀盾]` ✓ |
| **拆箭塔** | 100 座 → 0，拆完自动转打守军 → 15 回合胜 ✓ |

> 验"防御减伤"为什么要取**首回合**：整场对比会被两件事掩盖 ——
> ① 伤害饱和（一次齐射打光对方，两种动作的结果都是"全灭"）；
> ② 阵位差（防御 50 / 前进 100，距离差 50，衰减档位可能不同）。首回合双方都还没推进 → 唯一变量就是减伤。

### 设置界面

照原版位置：**校场 → ⚔️ 出征战术**（每兵种一行动作 + 一行目标，目标含"箭塔"），
分页每页 4 个兵种（弹窗内禁止滚动条）。点选即存、**只切 class 不重绘**（与全站点选一致）。
出征弹窗显示本次带的战术 + "调整"入口。

**只做攻方战术**：本作守方是 NPC，没有可指挥的场合 —— 做一个没人能用的"防守战术"入口就是死数据。

### 关于第 6 条（我自己造成的，值得单独说）

## 三 资源与人口归属城池（需求 4 上半）

老板：「将领，人口，资源等是归属于城池的数据，切换城池时，只统计、呈现当前的数据即可」

### 实现路线：**访问器**，不是"把 115 处 `s.res` 逐个改掉"

`state` 上的 `res` 定义成 **getter**，永远指向**当前城池**的 `city.res`：

```js
Object.defineProperty(st, 'res', {
  get: function () { return GAME.res(); },   // GAME.res(city) = (city||当前城).res
  enumerable: false,                          // 存档里不出现全局 res 字段
  configurable: true,
});
```

三个好处：
1. 旧代码 `s.res.gold -= x` **一行不改**，语义自动变成"扣当前城池的金"；
2. 不可能"改一处忘一处"—— 物理上只有一份数据，getter 就是唯一出口；
3. `enumerable:false` → 存档里**不会**出现顶层 `res`；每城自己那份 `city.res` 随正常序列化走。

### 配套改动

| 处 | 改动 |
|---|---|
| 产出结算 | `tickOnce` / `simulateBulk` 改为**逐城**结算（各城加进自己的库存、按自己的仓容封顶） |
| 军队耗粮 | 新增 `GAME.foodPerSecOf(city)`，各城军队吃自己城的粮；断粮逃兵只饿该城的兵 |
| 将领俸禄 | 从**该将所在城**扣 |
| 人口增长 | 逐城向本城民房上限爬升 |
| 仓储上限 | `storeCap` → `storeCapOf(city)`（唯一出口），按本城各仓等级之和 |
| 全境合计 | `productionPerSec()` 重写为 **Σ cityProdPerSec** + 爵位俸禄（记在首城），不再是"另一套算法" |
| 全境人口 | 新增 `GAME.totalPop()` / `totalPopCap()`；**任何"总人口"都必须走它**（直读 `s.res.pop` 只代表当前城） |
| 将领归属 | 新增 `GAME.genCityOf(g)`：`cityId` 为空时归当前城 —— 不兜底的话这些人会从"本城"名单里凭空消失 |
| 存档迁移 | 旧档顶层 `res` **整份并入首城**，其余城池按等级补一笔（`npcCityRes`） |

### 界面

## 五 本轮抓到的一个真 bug（护栏抓的）

**攻占后 `col/row` 没跟着 `cells` 换** —— `onConquer` 用满配布局替换了 `cells`（40 格），
但 `col/row` 还是 `makeCity` 的默认 8×6 → **"40 格却按 8×6 渲染"**，行列全错。

`ui.cityHTML` 是用 `idx % COLS` / `Math.floor(idx / COLS)` 定位格子的，
`COLS` 取 `c.col` —— 所以格数与 col/row 必须同源。已修：

```js
newCity.col = sh.col;   // ⚠️ col/row 必须跟着 cells 一起换！
newCity.row = sh.row;
newCity.cells = sh.cells.map(...);
```

护栏：`实测：攻占后建筑与格数就地转正（拿到的就是满配城）` ——
这条在破坏测试里对"故意不设 col/row"精确变红。

## 一 设计：两个来源，**一个出口**

箭塔从此有两个来源，但战斗与界面只认一个数：

```
来源① 城防折出   每 2 点城防 = 1 座（v59 照搬原版，玩家城与 NPC 城都有）
来源② 作坊建造   玩家在工匠作坊里花资源造的（存 city.towers，只有玩家城有）
                    ↓
        GAME.towerCountOf(city)  ← **唯一出口**
                    ↓
        城头火力（tactic 的 towerStart）＋ 守备力（cityDefense）
```

### 为什么要拆 `cityDefenseBase` / `cityDefense`

箭塔座数由城防折出，若城防又把箭塔算进去 → **互相喂的循环**。所以：

- `GAME.cityDefenseBase(city)` = 城防本体（驻防 + 城墙×20 + 专精 + 天时 + 守将），**不含箭塔**；
- `GAME.cityDefense(city)` = Base + 自建箭塔 × `homeDef`（给界面与"守军减伤 defBonus"用）；
- `GAME.towersFromDef(city)` 只从 **Base** 折出。

### "默认参与防守"怎么落地

- 造好即计入 `towerCountOf` → 城头火力自动上阵，**不需要任何指派或开关**；
- 同时计入 `cityDefense` → 守备力上升 → 攻城方的 `defBonus`（守军减伤）提高。
- 战斗侧不自己折数，只在 `opts.towers` 里**传数**；引擎用 `T.towerCountOfArg(defVal, opts.towers)` 取。
  NPC 城不传（`city.towers` 未定义）→ 走老路，**v59 已标定的平衡不漂**。

## 六 ⚠️ 本轮踩到的脚本事故（记下来别再犯）

我写了个"批量修闭包写法"的脚本，用了 `s[:start] + s[end:]` 来删区间 ——
**当 `start > end` 时这个拼接会把中间那段复制一份**（不是删除）：
smoke 里凭空多出 **72 条重复断言**（v60 + v61 两段被复制）。

例如"城内地块改用 SVG 图标"在 v39 与 v40 各有一条 —— 那是原有工程卫生问题，不是本轮造成的）。

**教训**：删除区间前必须先断言 `start < end`，否则"删除"会变成"复制"；
而且改完之后要跑一次**重复名检查**（`grep -o "check('[^']*'" | sort | uniq -d`）——
只数总数是看不出来的（总数只多了 72，很容易被当成"新加了很多断言"）。

## 一 野外城每日限掠一次

口径（老板给的是"只能被掠夺一次"，我按一线规则实现）：

## 二 名城：补满建筑（按其等级上限）

## 五 守将属性只对当前城池加成

老板：「守将属性只对当前城池起加成作用，不同城市有不同的守将」。

**根因**：`GAME.guardBonusTotal()` 把**全境所有守将**的加成累加起来，
再拿这个总数去算产量、建造、征兵、研究 —— 一个 B 城的守将能给 A 城加成，
甚至"哪座城"加起来都一样。而 `cityProdPerSec(city)` 明明按城算基数，
却是"本城的基数 × 全境的加成"，切城时数字还动。

**处置**：删掉 `guardBonusTotal`（不留后门），四个消费点全部改成**读本城守将**：

| 消费点 | 改后 | 说明 |
|---|---|---|
| 产量 | `GAME.prodFactors(r, city)` ← `GAME.guardBonus(city)` | 单城产量与瀑布分解都传城 |
| 建造 | `GAME.guardBuildMult(city)` | 6 处调用点全部带城 |
| 征兵 | `GAME.guardBonus(city).train` | 哪个军营募兵就吃哪座城的守将 |
| 研究 | `S.research(techId, cityId)` | 研究是全境科技，但加成取**发起城** |

结果（实测）：A 城守将 内政 +61%、B 城守将 内政 +47% —— 各算各的；
A 城立守将，B 城的产量因子**不含**守将项；建造加速同理（没守将的城系数一点不动）。
未占据名城的守将本来就是"每城一个"（按城 id 确定性派生），同等级两座城不是同一个人。

### 几何探针抓出来的两个真问题（jsdom 量不出高度，只能靠真浏览器）

1. **建造选择弹窗正文超出 18px** → 弹窗内冒出滚动条（老板明令禁止）。
   原因：图标从 emoji 换成 84px 位图后卡片变高，`lg`（860×600）装不下 →
   **提到 `xl`（960×min(700,88vh)）**，并给图标固定高度 84px + `width:auto`
   （位图长宽比不一致时不会被拉变形，卡片也才等高）。
2. **据点一览超出弹窗高度**（1600×950 也超 108px、720p 超 256px）——
   列一多行一多就会顶出去。→ 改成**分页**（`ui.modalPage('forts', …, 6)`，每页 6 行；
   实测 8 行在 720p 仍超 44px）。加上「地块/状态」两列之后三种分辨率全部不超。

> ⚠️ 探针方法论（v63 记一笔）：**必须先开弹窗 → 等布局稳定 → 再单独量**。
> 在同一个 `evaluate` 里"开完立刻量"会量到还没加载完的图标（假红 8 个破图），
> 甚至量到上一次关闭时的残留面板（假绿 2 条）。量元素一律用 `#modal-root .inner-panel`，

## 一 城墙纳入自动建造

**改前的毛病**：城墙**不占格**（等级存在 `city.wallLv`），所以它不在格子列表里；
而自动升级（`GAME.autoUpgrade`）只遍历「城内容格 + 城外资源地块」——
城墙**一次都没被自动升过**，等级永远停在你手动点的那一级。

**改后**：城墙作为**每城一个**候选参与自动升级，等级序与别的建筑同一条规则。

- 候选：`{ kind: 'wall', cityId, lv: wallLv }`，执行走既有的 `GAME.buildWall(cityId)`
  （0 级 → 修墙，≥1 级 → 升墙，函数内部已分派）。
- 同级排序：**城内功能建筑 → 城墙 → 城外资源地块**
  （城墙耗石尤多，同级时不该抢在城内建筑前面；但 0 级城墙天然等级最低，会最先修）。
- 满级判定跟着含城墙：`全部建筑已满级（含城墙）`。
- 多城经营时**每座城各自修墙**（`city.wallLv` 是城属性）。

### ⚠️ 本轮自己抓出来的一个真 bug：城墙会**重复排队**

城墙没有 `cell.pending` 可看，第一版候选只判断"等级未满"→ 自动升级**每 tick 都会再排一次城墙**：
重复扣石料、同一个等级付好几份钱、建造队列位被同一条城墙占满。
新增唯一出口 `GAME.wallPendingOf(cityId)`（"该城是否已有城墙在队列里"），候选里先查它。
**这个 bug 是破坏测试（第 2 类）发现的 —— 它让"两座城各自修墙"那条断言也一起红了。**

## 二 将领席位按城

### 改前的毛病

`GAME.generalCap()` 读的是**当前城**的招贤馆等级，却拿去约束**全境总数**
（`s.generals.length >= cap`）。于是两件事都说不通：

- 多城经营时席位**不随城数增加**（第二座城的招贤馆白建）；
- 切到招贤馆小的城，反而**连一个人都不许招** —— "到底哪个城的容量"没法回答。

### 改后（席位跟着城走，一个出口）

| 出口 | 含义 |
|---|---|
| `GAME.genSlotsOf(city)` | 该城席位数 = 该城招贤馆等级 +（该城招贤馆满级专精 ? 2 : 0） |
| `GAME.generalsIn(city)` | 该城将领（**与将领页名单同源**：都走 `genCityOf`） |
| `GAME.genFreeOf(city)` | 剩余席位（负数按 0 记） |
| `GAME.genSlotsTotal()` | 全境合计（**只给"全境"视图显示**，不参与任何判定） |

`GAME.generalCap` **已删除**（留函数就是留后门）。

**规则**：

- **招募**（客栈）：名额按该城算、黄金从**该城**扣、人落在**该城**
  （`GAME.innRecruit(cid, cityId)` 从"当前城"改成显式传城）。
- **派遣**：目标城必须还有空位（`GAME.doDispatch` 拦截）；
  没招贤馆 = 0 席，提示会区分"尚无招贤馆"与"招贤馆已满"。
- **超编不清退**：现有将领不会被赶走，但**不许再进人**。
  开局首城没有招贤馆（0 席）却有 1 位君主 —— 显示成 `1 / 0 席`，这是事实，界面里说明了。
- **降将也有归属**：`grantHero(npcCity, fromCity)` 落到**出征的出发城**（谁打下来归谁），
  不再是无主之将。读档时 `GAME.normalizeGenCities()` 把 `cityId` 为空/指向已不存在城池的
  将领挂到首城（否则他会随"我现在在看哪座城"飘来飘去，席位统计跟着飘）。

**四处界面都写清楚**（几何探针逐项复核）：

| 位置 | 呈现 |
|---|---|
| 将领页 | 标题 `本城 N / M 席 · 全境 X / Y 席`（本城栏比本城、全境栏比合计） |
| 客栈 | `许都 招贤馆空位 1/3` |
| 招贤馆 | `房间（本城将领席位）N/M` + `全境席位 …（各城合计 K 席）` + 满员时的两条出路 |
| 派遣 | 目标城 chip：`2/3 席（空 1）` / `（已满）`；提示写明"席位按城算" |

### ⚠️ 本轮踩的两个方法论坑（已写进技能/记忆）

1. **破坏测试被打断会留下注入**：上一版脚本跑得久，bash 超时发了 SIGTERM →

   现在脚本改为：**先备份 → 启动时若发现备份就先还原 → 每例后从备份还原 →

2. **夹具本身要能区分**：e2e 里"将领页本城席位"那条原本每次都可能等于全境合计

   补了一座**有招贤馆的侧城**并加一条"本城席位与全境合计必须能区分"的前提断言。
   **判据与被测对象不能是同一个数 —— 这是"断言守不住"的又一种形态。**

另修掉一条**偶发断言**：e2e「每队列限 1 次：韩信三篇被标记已用」钉死了具体宝物，
而加速弹窗列的是**所有可用宝物**、点到的可能不是它 → 改为**点哪件断言哪件**（按钮带 `data-item`）。

**精确值进 `title` 悬停**（要看确切数目时把鼠标放上去），屏幕上只给短写。

**"齐整"的实现在 CSS**：资源行的 `.val` 由 flex 改 **grid**（`78px 62px 1.1em`），
金额独占第一格右对齐 —— 否则各行金额的右缘取决于它右边还有什么（增速/加号/宝物徽标），
实测右缘 148 vs 169 对不齐；改 grid 后五行**右缘全部 169**。

## 4 · 系统城统一 8×6 + 名城建筑满级

### 「怎么现在变成 4×8 了？」

老板**没看错**：v63 的格数档位是 `1~2 级 6×4 · 3~4 级 8×4 · 5~6 级 8×5 · 7 级及以上 8×6`，
他随手点到的低等级城就是 8 列 **4 行**。v65 按他的口径**取消分档**：

```
DATA.CITY_PLAN.size = [8, 6]     // 唯一来源，1~10 级一律 8 列 × 6 行 = 48 格
```

`sizeByLevel` 档位表**已删**（所有档位填同一个值就是死数据）。官府仍按
`makeCity` 那套公式落位（右侧第 2 列起、垂直居中），探针逐级复算过 1~10 级的官府 4 格位置。

### 名城默认满级

老板：「名城默认满级（如县城 12，郡城 14，州城 18 等）；城内外建筑也达到等级上限」

```
GAME.npcBuildLvOf(city) =
  名城：min(MAX_LEVEL_ABS, DATA.CITY_PLAN.maxLevel(=10) + cityBuildBonus(city))
  非名城（野外城池）：按**自己的等级**
```

实测：**都城 22 · 州城 18 · 郡城 14 · 县城 12**（改前是 `城等级 + 加成` → 州城 17、县城 7）。

- 城内地块与**城外地块**都补到该上限（`extGrid` 的每块地等级 = `bl`）；
  块数仍按城等级（= 该城官府等级）—— 两者不是一回事：块数是"官府能管多少地"，
  等级是"这地开发到什么水平"。
- 城墙等级 = 建筑上限（攻城的箭塔射程跟着它走）。
- 野外城池**不给**满级（据点随等级长起来；给它们上满级会凭空变出一座座满配城）。

## 6 · 缺粮 24 小时后哗变，每 24 小时逃 20%

**改前**（`applyStarvation`）：粮一断就按**缺口占需求的比例**逃兵（单次封顶 15%/tick）——
规则说不清，而且断粮当场掉兵，玩家根本来不及救。

**改后**（老板给定）：

```
DATA.STARVE = { hours: 24, mutinyPct: 0.2 }
GAME.mutinyOf(city)                       // 一次哗变：各兵种逃**当前数量**的 20%
GAME.starveStep(city, starving, gameHours) // 计时与"每满 24 小时来一次"的推进
```

- **在线 tickOnce 与离线 simulateBulk 共用 `starveStep`**（两套口径漂移是这个项目的老毛病）。
- 粮一接上就**清零重计**（否则"断断续续缺粮"会攒够 24 小时突然哗变，玩家看不懂）。
- 各兵种**分别**逃 20%，向下取整（不到 5 人的小队不会归零消失）。
- 侧栏断粮警示改成报**还能撑多久**：`🕯 粮尽，无法出征。守军尚可支撑 12 游戏小时，逾将哗变逃散（每 24 小时各兵种逃 20%）。`
- 实测：`100000 →（24h）80000 →（48h）64000`；离线推进 72 小时 = 连逃 3 次。

### 本轮踩到并记下的坑

1. **断言的前置条件必须固定**（连跑 4 次才抓到）：e2e 里"侦查面板给出准确数量"偶发变红 ——
   根因是**天气随机**，大雾会让情报整体降级。修法：把天气固定为 `clear`，
   并把将领体力/精力补满（侦察要消耗它们，不足时 expedition 直接拒绝）。
2. **DOM 断言的"引用"是活的**：`document.querySelector('#modal-root')` 拿到的节点
   每次 `openModal` 都换内容 → 中间若被别的断言重开成另一页，后面的 DOM 断言读到的就是那一页。
   修法：DOM 断言紧跟在自己那次打开之后，或改判**数据层**（`sr27b.totalExact`）。
3. **`getClientRects()` 数折行必须只选文本节点**：`selectNodeContents(td)` 会把元素盒也算进去，
   恒返回 >1（六个属性全部"假红折行"）。
4. **"注释骗过断言"第 10 次**：`simulateBulk` 的注释里写着"走同一个 starveStep"，
   结构断言没剥注释 → 破坏测试第 5 类第一版注入**零反应**。修法：`stripComment`。
5. **真 bug**：`expedition` 的 scout 返回**漏了 `gNum`** → 面板显示「约 undefined 名」。
   是 e2e 抓到的；已补结构断言（`gNum: sc.gNum`）防止再漏。
6. **`ui._scoutPage` 的记忆**：翻页状态是全局的，别的断言翻到第 2 页会影响后面 ——
   真实入口（`onMarchArrive`）已改成**显式传 0**。
